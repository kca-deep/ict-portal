# 6회차 - 오픈 전 하드닝 + 관리자 쿼리로그 페이지(로그인 없이 운영)

> 이 문서는 **현재 프로덕션 상태를 반영한 구현계획**이다.
> 이번 회차는 **기존 챗봇 화면(`app/page.tsx`·`components/**`)은 일절 건드리지 않는다.** 다만 **관리자 전용 신규 페이지**(쿼리로그 확인용)는 새로 추가한다 — 기존 화면을 수정하지 않으므로 "사용자 화면 무변경" 원칙은 유지된다.

> **⚠️ 설계 결정 변경 (문서 갱신 필요)**
> 이번 회차부터 **이 서비스는 로그인 없이 운영**한다. 이는 `CLAUDE.md`·`docs/00`·`docs/07` §1("채팅 로그인 필수, 초대·승인 기반 계정")과 **배치되는 결정**이다. 함의: ⓐ 사용자 식별을 **요청 IP**로 한다(인증 주체 없음). ⓑ `query_log`의 `user_id`(auth.users FK)·본인/관리자 **RLS 정책은 무의미**해져 제거한다. ⓒ 관리자 페이지는 로그인 대신 **service_role 서버 조회 + 관리자 비밀번호**로 보호한다. ⓓ 쿼리·IP를 인증 없이 수집·열람하므로 **민감도가 올라간다**(보존·접근통제는 7장·`docs/07` §10). → **`CLAUDE.md`·`docs/00`·`docs/07`를 no-login 기준으로 갱신해야 한다(별도 작업).**

|------|------|
| 날짜 | 2026-06-22 주 (이번 주) |

> **이번 회차 한 줄 요약**
> 5회차로 **기능은 다 됐다.** 그런데 지금 프로덕션은 **색인 API가 무인증으로 열려 있고, 에러 원문이 사용자에게 그대로 나가고, 요청 횟수·입력 길이에 상한이 없고, 운영 로그가 한 줄도 안 쌓인다.** 이대로 외부에 열면 비용 폭주·데이터 오염·정보 유출 위험이 있다. 이번 주는 **로그인 없이 운영**한다는 전제 위에서, **기존 챗봇 화면은 그대로 두고** 서버(API·설정·DB)를 단단히 하고, 운영자가 무슨 일이 일어나는지 볼 수 있도록 **IP 기반 쿼리로그**를 쌓아 **관리자 페이지**에서 확인하게 만든다.

## 1. 이번 주 순서 (위험 크고 노력 작은 것부터)

| 순서 | 장 | 무엇을 | 왜 이 순서인가 | UI |
|---|---|---|---|---|
| **1** | **2장 색인 API 잠금** | `/api/ingest`를 비밀키 없으면 404 | **가장 위험.** 무인증 DB 쓰기를 즉시 닫는다 | 기존 화면 무변경 |
| **2** | **3장 입력·에러 방어** | 입력 길이·턴 상한 + 에러 일반화 | 노력 작고 효과 큼(유출·폭주 차단) | 기존 화면 무변경 |
| **3** | **4장 레이트리밋** | IP 분당 상한 | 비용 폭주의 1차 방벽 | 기존 화면 무변경 |

> **참고**: 로그인은 도입하지 않기로 했다(상단 설계 결정 변경). 따라서 이전에 "다음 회차로 이월"했던 *로그인 게이트*는 **계획에서 제거**된다 — 대신 IP 기반 책임추적 + 관리자 비밀번호로 운영한다.

## 2. [백엔드] 색인 API 잠금 — `/api/ingest`

### 2-1. 무엇을 고치나

`/api/ingest`는 지금 **누구나 호출**할 수 있고, 호출되면 **관리자 권한(`service_role`)으로 `documents` 테이블에 직접 쓴다**(`ingest/route.ts:24` POST 진입 → `:35` `getSupabaseAdmin()`). 외부에 노출되면 **임의 문서 주입으로 검색 결과를 오염**시킬 수 있다. `docs/07` §4.4의 Critical 항목이다.

### 2-2. 해법 — 공유 비밀키 헤더(스크립트 전용화)

색인은 **운영자/스크립트만** 쓰는 기능이므로, **로그인 UI 없이** 잠글 수 있다. 환경변수 `INGEST_SECRET`을 두고, 요청 헤더 `x-ingest-secret`이 일치하지 않으면 **존재를 숨겨 404**로 응답한다(401은 "여기 뭔가 있다"는 신호가 되므로 404가 안전). 색인 스크립트(`scripts/*`)는 이 헤더를 달아 호출한다. **DB·화면 변경 없음.**

| 단계 | 작업 | 위치 |
|---|---|---|
| 1 | `INGEST_SECRET: z.string().min(1)` (프로덕션 필수) | `lib/env.ts` |
| 2 | POST 진입 첫 줄에서 `x-ingest-secret` 검증, 불일치 시 `404` | `app/api/ingest/route.ts:24` |
| 3 | 색인 호출 스크립트에 헤더 추가 | `scripts/**`(색인 호출부) |

### ▶ 사용자 프롬프트 — 2장

> 우리 문서 색인 기능 `/api/ingest`가 지금 **아무 인증 없이** 열려 있어서 누구나 우리 데이터베이스에 글을 밀어 넣을 수 있어. 이건 운영자만 쓰는 기능이니까, **비밀키를 아는 호출만** 받게 막아 줘. 환경변수로 비밀키를 하나 두고, 요청 헤더의 비밀키가 맞지 않으면 **그냥 404(없는 주소)인 것처럼** 응답해 줘(괜히 401로 "여기 뭔가 있다"고 알려 주지 말고). 그리고 우리가 색인할 때 쓰는 스크립트에는 그 비밀키 헤더를 붙여 줘. **화면은 건드리지 말고.**

## 3. [백엔드] 입력·에러 방어 — `/api/chat`, `/api/ingest`

### 3-1. 입력 길이·턴 수 상한

지금 `isValidMessages`(`chat/route.ts:136-148`)는 **메시지가 비었는지(공백)만** 본다. 질문 한 개의 길이도, 대화 턴 수도 상한이 없어서 **거대한 입력 한 방으로 LLM 컨텍스트·비용을 폭주**시킬 수 있다.

- `MAX_QUESTION_LEN`(예: 4,000자) 초과 질문 → `400`.
- `MAX_TURNS`(예: 20) 초과 대화 → 오래된 턴을 자르거나 `400`.

### 3-2. 에러 일반화

지금 에러 **원문**이 사용자에게 그대로 간다 — `chat/route.ts:327`의 `message: (err as Error).message`, `ingest/route.ts:46-49·69-72`의 임베딩/insert 에러 원문. 외부 API 키 일부·DB 구조 등 **내부 정보가 새어** 나갈 수 있다. 원문은 **`console.error`로 서버 로그에만** 남기고, 클라이언트엔 **"일시적인 오류가 발생했어요. 잠시 후 다시 시도해 주세요." 같은 일반 메시지**만 보낸다. (스트림의 `error` 이벤트 **모양은 그대로** 두고 `message` 내용만 일반화 → 화면 무변경.)

| 단계 | 작업 | 위치 |
|---|---|---|
| 1 | `MAX_QUESTION_LEN`·`MAX_TURNS` env 추가 | `lib/env.ts` |
| 2 | `isValidMessages`에 길이·턴 상한 | `app/api/chat/route.ts:136-148` |
| 3 | catch에서 원문은 `console.error`, 클라이언트엔 일반 메시지 | `chat/route.ts:326-327`, `ingest/route.ts:46-49·69-72` |

### ▶ 사용자 프롬프트 — 3장

> 두 가지를 막아 줘. **첫째, 입력 상한.** 지금은 질문이 비어 있는지만 보는데, **질문 한 개의 글자 수 상한**과 **대화 턴 수 상한**을 환경변수로 두고 넘으면 정중히 거절(또는 오래된 대화 잘라내기)하게 해 줘. **둘째, 에러 가리기.** 지금 서버에서 에러가 나면 그 **원문 메시지가 사용자한테 그대로** 가는데, 원문은 **서버 로그에만** 남기고 사용자에겐 **"일시적인 오류가 발생했어요" 같은 일반 안내**만 보내 줘. 화면이 받는 이벤트의 **모양(형식)은 그대로** 두고 안에 담기는 문구만 바꿔서, **화면 코드는 안 건드리게** 해 줘.

## 4. [백엔드] 레이트리밋 — 분당 요청 상한

### 4-1. 무엇을·왜

요청 횟수 상한이 전혀 없어서, 한 사람이 **분당 수백 번** 때리면 OpenAI·Cohere·Anthropic 비용이 그대로 폭증한다. **로그인 없이 운영**하므로 **요청 IP 기준**으로 분당 상한(`RATE_LIMIT_PER_MIN`)을 두고, 초과 시 `429`로 막는다. 이때 추출한 IP는 **5장의 `query_log.ip`와 같은 소스**를 쓴다(IP 추출 헬퍼 1개를 레이트리밋·로그 적재가 공유).

### 4-2. PoC용 경량 구현 + 솔직한 한계

Vercel 서버리스는 **요청마다 다른 인스턴스**에서 처리될 수 있어, 인스턴스 메모리 카운터(in-memory)는 **완벽한 전역 카운트가 아니다**(인스턴스가 여러 개면 각자 셈). 그래도 **무방비보다 훨씬 낫고** PoC "라이트 셋업" 원칙에 맞으므로 **경량 in-memory best-effort**로 시작한다. 트래픽이 늘면 **Upstash Redis / Supabase 카운터**로 승격(별도 인프라라 지금은 도입하지 않음 — 한계만 명시).

| 단계 | 작업 | 위치 |
|---|---|---|
| 1 | `RATE_LIMIT_PER_MIN` env 추가 | `lib/env.ts` |
| 2 | IP 추출 + 분당 카운터(슬라이딩/고정창) 헬퍼 | `lib/ratelimit.ts`(신규, 백엔드 전용) |
| 3 | `/api/chat`·`/api/ingest` 진입부에서 초과 시 `429` | `chat/route.ts:150`, `ingest/route.ts:24` |

> **주의**: 경량 카운터의 한계(인스턴스별·콜드스타트 시 리셋)를 주석과 `docs/07`에 명시한다. "레이트리밋 = 완전 차단"으로 오해하지 않게.

### ▶ 사용자 프롬프트 — 4장

> 지금 누가 우리 챗봇 API를 **분당 수백 번** 호출해도 막을 게 없어서 비용이 그대로 새. 아직 로그인이 없으니 **요청한 곳(IP) 기준으로 1분에 N번**까지만 받고 넘으면 **429(너무 잦음)**로 돌려보내 줘. N은 환경변수로 두고. 다만 우리가 Vercel 서버리스라 **인스턴스가 여러 개면 카운트가 완벽하진 않다**는 걸 알아 — 지금은 가벼운 메모리 방식으로 시작하고, **그 한계를 주석과 보안 문서에 적어** 둬. 새 외부 서비스(레디스 같은 것)는 **지금 도입하지 말고**. 화면은 그대로.

## 5. [백엔드 + DB] 감사 로그 적재 — `query_log`

### 5-1. 무엇을·왜

`docs/07` §6과 CLAUDE.md는 "`query_log`에 질의·답변·인용·지연·토큰을 적재한다"고 적었지만, **실제 `app/api/chat/route.ts`에는 insert가 한 줄도 없다.** 운영의 눈(사용량·지연·인용검증율·분기 비율)이 **전혀 안 쌓이는** 상태다. 게다가 기존 `query_log` 테이블은 파이프라인의 **핵심 신호를 담을 컬럼이 없다** — 분기 결과(`route`)·관련도(`top_score`)·게이트 결과가 들어갈 자리가 없고, 인용검증도 단일 boolean뿐이라 조문별 verdict 배열을 손실한다.

그래서 이번 장은 **(A) 테이블을 파이프라인에 맞게 보강**하고 → **(B) 실제 적재 코드를 넣는다.**

### 5-2. 파이프라인이 실제로 산출하는 값 (적재 대상)

한 요청이 `route.ts`를 흐르며 만드는 값. **대부분 이미 변수로 존재**하므로 그대로 담으면 된다.

| 적재 항목 | 파이프라인 산출 | 코드 위치 | 비고 |
|---|---|---|---|
| **`ip`** | 요청 IP(`x-forwarded-for` 첫 주소) | 4장 IP 헬퍼 공유 | **신규 — user_id 대체(no-login)** |
| `query` / `answer` | 질문 / 답변 전문 | `route.ts:168`, `:258-264` | 보존정책: `docs/07` §10(IP·전문 보존기간 후 삭제/마스킹) |
| `message_count` | `messages.length`(턴 깊이) | `route.ts:158` | 신규 컬럼 |
| **`route`** | `out_of_scope`/`law`/`regulation` | `route.ts:206-207, 250` | **신규 — 가장 중요** |
| **`top_score`** | 재정렬 최상위 관련도 `maxScore` | `route.ts:194` | **신규** |
| `below_threshold`·`gate_sufficient`·`out_of_scope` | 분기 판정 근거 | `route.ts:195-207` | 신규(튜닝용) |
| `retrieved_doc_ids` / `retrieved` | 재정렬 상위 문서 id(+score) | `route.ts:181` | 평가용 |
| `law_refs` | `[{name,lawId,score}]` | `route.ts:244-247` | 법령 분기 시 |
| `cited_law_refs` / `citation_*` | `citationCheck.verdicts`(body 제외)·환각 여부·개수 | `route.ts:270-323` | verdict 배열 보존 |
| `llm_model` | `env.LLM_MODEL` | `route.ts:338` | |
| `retrieval_ms`·`rerank_ms`·`llm_ms`·`ttft_ms`·`total_ms` | 단계별 지연 | — | **계측 추가 필요(5-4)** |
| `tokens_in`·`tokens_out` | 답변 호출 usage | — | **usage 노출 필요(5-4)** |

### 5-3. (A) 테이블 보강 — 신규 마이그레이션 (단독 PR)

PoC 원칙상 **기존 `20260520000004_query_log_table.sql`은 수정하지 않고**, no-login 정리·빠진 컬럼·인덱스를 **신규 마이그레이션**으로 더한다.

- 파일: `supabase/migrations/20260622000001_query_log_enrich.sql`
- **no-login 정리(제거)**: 본인/관리자 RLS 정책(`query_log_select_self`·`*_admin`)·`query_log_user_idx`·**`user_id` 컬럼** drop (로그인 없으면 무의미)
- **추가 컬럼**: **`ip`**·`message_count`·`answer_truncated`·`route`(+check)·`top_score`·`below_threshold`·`gate_sufficient`·`out_of_scope`·`retrieved`·`law_refs`·`citation_count`·`citation_verified_count`·`has_hallucination`·`ttft_ms`·`error_code`
- 추가 인덱스: `ip`(IP별 사용량), `route`(분기 비율), `has_hallucination`(환각 추적, 부분 인덱스)
- **RLS**: enable 유지하되 authenticated/anon 조회 정책 **없음**(= 공개 키로 조회 불가). 적재·관리자 조회는 **service_role 전용**(RLS 우회).
- 재사용: `retrieval_ms`·`rerank_ms`·`llm_ms`·`total_ms`·`cited_law_refs`·`citation_verified`·`tokens_*`(기존 컬럼 그대로)

> 적용: `pnpm db:push` (ALTER … ADD/DROP … IF (NOT) EXISTS 라 재실행 안전).

### 5-4. (B) 적재 코드 — `route.ts` 두 군데만 손봄

대부분은 이미 있는 변수라 그대로 담지만, **두 가지만 새로 측정**한다. 둘 다 UI 무관:

1. **지연 계측** — `route.ts`에 `Date.now()` 몇 줄. `t0`(시작) → 검색 후(`retrieval_ms`) → 재정렬 후(`rerank_ms`) → 첫 delta(`ttft_ms`, `route.ts:263` 루프 첫 진입) → 스트림 종료(`llm_ms`) → done(`total_ms`).
2. **토큰 usage 노출** — `ragChatStream`(`lib/ai/llm-router.ts:181`)이 텍스트만 yield하고 usage를 버린다. `stream.finalMessage()`의 `usage`(input/output tokens)를 반환해 route가 받게 변경. ※ 범위·적합성 게이트(`max_tokens:8`)도 토큰을 쓰지만 미미 — 답변 호출 usage만 적재(필요 시 합산은 후속).

| 단계 | 작업 | 위치 |
|---|---|---|
| 1 | 적재 헬퍼 `logQuery(row)`(service_role insert) | `lib/db/query-log.ts`(신규) |
| 2 | 단계별 `Date.now()` 계측 | `app/api/chat/route.ts` |
| 3 | `ragChatStream`이 최종 `usage` 반환 | `lib/ai/llm-router.ts:181-222` |
| 4 | `done` 이벤트 직후 **비동기 호출(await 안 함)** | `app/api/chat/route.ts:325` 부근 |

설계 원칙:
- 사용자 식별은 **`ip`**로 한다(로그인 없음). 4장 레이트리밋이 쓰는 IP 추출 헬퍼를 그대로 재사용 — 같은 요청의 IP가 레이트리밋과 로그에 일관되게 들어간다.
- **insert는 service_role**(RLS 우회). **실패가 사용자 응답을 막지 않도록** fire-and-forget + `try/catch` + `console.error`만.

### ▶ 사용자 프롬프트 — 5장

> 우리 문서엔 "질문·답변 로그를 `query_log`에 쌓는다"고 적혀 있는데 **실제로는 한 줄도 안 쌓이고 있고**, 게다가 그 테이블엔 우리 챗봇이 만들어내는 **분기 결과(규정/법령/범위밖)·관련도 점수·인용 검증 상세**를 담을 칸이 없어. 그래서 두 가지를 해 줘.
>
> **첫째, 테이블 보강.** 기존 마이그레이션은 건드리지 말고 **새 마이그레이션 파일 하나**로, 빠진 칸들(분기 결과·관련도·게이트 결과·인용 검증 개수/환각 여부·첫 토큰 지연 등)을 컬럼으로 추가하고, 분기·환각을 빨리 찾을 인덱스도 더해 줘.
>
> **둘째, 적재 코드.** 답이 끝난 뒤에 채팅 처리 코드 안에 **이미 있는** 분기·관련도·인용검증·답변 값과, **새로 잰** 단계별 시간·토큰 사용량을 그 테이블에 **비동기로(응답을 늦추지 않게)** 저장해 줘. 저장하다 실패해도 **사용자 답변은 절대 막히지 않게** 조용히 로그만 남기고. 우리는 **로그인 없이** 운영하니 작성자 대신 **요청 IP**를 저장해(4장 레이트리밋이 쓰는 그 IP와 같게). 화면은 그대로.

> 붙이기 전 한 번 확인할 것: 질문 몇 개를 던진 뒤 `query_log`에 **행이 쌓이고**, `route`·`top_score`·`has_hallucination`·`ttft_ms`가 **실제 값으로 채워지는지** 확인해 줘.

## 6. [설정] 부팅 가드 복구 · 보안 헤더 · `vercel.json` · env 정합

화면과 무관한 **설정 위생**을 한 번에 처리한다.

### 6-1. 부팅 가드 복구 (env)

`lib/env.ts:8-12`의 `OPENAI_API_KEY`·`ANTHROPIC_API_KEY`·`COHERE_API_KEY`·`LAW_GO_KR_API_KEY`가 `.optional()`이라, **비어 있어도 부팅에 성공**하고 첫 호출에서야 터진다(CLAUDE.md "누락 시 부팅 실패"와 불일치). 이들을 **프로덕션에서 필수**로 만든다(예: `superRefine`으로 `NODE_ENV==="production"`이면 필수, 로컬 개발은 유연하게).

### 6-2. 보안 헤더 (`next.config.ts`)

`next.config.ts`에 `async headers()`를 추가해 `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `Strict-Transport-Security` 등을 전역 적용. (`docs/07` §11 Medium.)

### 6-3. `vercel.json` 드리프트 정리

`vercel.json`이 **존재하지 않는** 라우트(`app/api/[transport]/route.ts`, `app/api/search/route.ts`)를 참조한다. 실제 라우트(`chat`·`ingest`·`cron`·`health`·`duplicate-check`)에 맞게 정리한다.

### 6-4. `.env` 정합 (0-4의 후속)

2·3·4장에서 추가된 키(`INGEST_SECRET`·`RATE_LIMIT_PER_MIN`·`MAX_QUESTION_LEN`·`MAX_TURNS`)를 **`.env.local`과 Vercel** 양쪽에 넣는다. (커밋에는 값 없이 키 목록만 — `.env.example`은 정책상 복원하지 않음.)

| 단계 | 작업 | 위치 |
|---|---|---|
| 1 | 4개 키 프로덕션 필수화(superRefine) | `lib/env.ts:8-12` |
| 2 | 전역 보안 헤더 | `next.config.ts:3-12` |
| 3 | 없는 라우트 참조 제거·정합 | `vercel.json` |
| 4 | 신규 키를 `.env.local`/Vercel에 반영 | (배포 설정) |

### ▶ 사용자 프롬프트 — 6장

> 설정 위생 네 가지를 한 번에 정리해 줘. ① 환경변수 검증에서 **LLM·임베딩·재정렬·법령 키가 비어 있어도 부팅되는** 문제를 고쳐서, **운영(production)에선 이 키들이 없으면 부팅이 실패**하게 해 줘(로컬 개발은 지금처럼 유연하게). ② Next 설정에 **기본 보안 헤더**(클릭재킹 방지·MIME 스니핑 방지·HSTS 등)를 전역으로 켜 줘. ③ `vercel.json`이 **존재하지도 않는 API 경로**를 가리키고 있으니 실제 있는 경로에 맞게 정리해 줘. ④ 이번에 새로 생긴 환경변수들을 빠짐없이 적용하도록 안내해 줘. 전부 **화면과 무관**한 설정이야.

## 7. [신규 화면] 관리자 페이지 — 쿼리로그 뷰어

> 이번 회차에서 **유일하게 새 화면을 만드는** 장. **기존 챗봇 화면(`app/page.tsx`)은 건드리지 않고**, `app/admin/**`에 분리된 관리자 전용 페이지를 추가한다.

### 7-1. 무엇을·왜

5장이 `query_log`를 채우기 시작하면, 운영자가 **무슨 질문이 들어오고, 어디로 분기되고, 환각·오류·지연·비용이 어떤지** 볼 화면이 필요하다. `docs/07` §6.2가 말하는 "관리자 화면"을 PoC 수준(읽기 전용 표 + 간단한 요약)으로 만든다.

### 7-2. 접근 보호 — 로그인이 없으므로 "관리자 비밀번호 + service_role"

로그인이 없어 RLS 역할 분리를 못 쓰므로, 관리자 페이지는 다음으로 보호한다:

- **관리자 비밀번호**(`ADMIN_PASSWORD` env). 페이지 진입 시 비밀번호를 한 번 입력 → **httpOnly 쿠키**(서명/만료 포함)로 세션 유지. 비밀번호 입력 폼은 관리자 페이지 안에만 있고 **기존 챗봇 화면과 무관**.
- **데이터는 서버에서만 읽는다.** 쿼리로그 조회는 **서버 컴포넌트/route handler에서 `service_role`로** 수행(RLS 우회). 브라우저로 service_role 키가 절대 안 나가게.
- 미들웨어(`middleware.ts`)에서 `/admin/*` 경로에 쿠키 검사 → 없으면 비밀번호 폼으로.

> **대안(택1 가능)**: 비밀번호 대신 **IP 허용목록**(사무실 IP만 `/admin` 허용)도 가능 — 어차피 IP를 수집하므로 일관적. 기본은 비밀번호(어디서든 접근 가능), 더 엄격히 하려면 둘을 함께.

### 7-3. 화면 구성 (PoC — 읽기 전용)

| 영역 | 내용 | 소스 |
|---|---|---|
| 상단 요약 | 오늘/최근 질의 수, 분기 비율(규정/법령/범위밖), 환각 발생 건수, 평균 `total_ms`·`ttft_ms`, 토큰 합계 | `query_log` 집계 |
| 로그 표 | 시각·IP·질문(요약)·route·top_score·환각 여부·지연·토큰 | `query_log` 최근 N건 |
| 상세 보기 | 한 행 클릭 → 질문/답변 전문·인용 verdict·근거 doc_ids·law_refs | `query_log` 단건 |
| 필터 | 기간·route·환각만·IP | 쿼리 파라미터 |

### 7-4. 손대는 파일

| 단계 | 작업 | 위치 |
|---|---|---|
| 1 | `ADMIN_PASSWORD` env 추가 | `lib/env.ts` |
| 2 | `/admin/*` 쿠키 게이트 | `middleware.ts`(신규) |
| 3 | 비밀번호 검증 + 쿠키 발급 | `app/admin/login/` + `app/api/admin/login/route.ts`(신규) |
| 4 | 로그 조회(service_role) + 집계 | `lib/db/query-log.ts`(5장 헬퍼 확장: `listQueryLogs`·`queryLogStats`) |
| 5 | 관리자 화면(서버 컴포넌트, 표·요약·상세) | `app/admin/page.tsx`(신규) |

> **기존 화면 무변경 확인**: 위 파일은 모두 `app/admin/**`·`middleware.ts`·`app/api/admin/**` 신규. `app/page.tsx`·`components/**`는 손대지 않는다.

### ▶ 사용자 프롬프트 — 7장

> 우리는 **로그인 없이** 서비스를 운영하지만, 운영자가 **무슨 질문이 들어오고 어디로 분기되는지·환각/오류/지연/비용이 어떤지**를 볼 **관리자 전용 페이지**가 필요해. **기존 챗봇 화면은 절대 건드리지 말고** `app/admin` 아래에 **새 페이지**로 만들어 줘.
>
> 로그인이 없으니 이 페이지는 **관리자 비밀번호**(환경변수)로 막아 줘 — 처음에 비밀번호를 한 번 넣으면 **httpOnly 쿠키**로 유지되고, `/admin` 경로는 미들웨어가 쿠키를 확인해서 없으면 비밀번호 입력으로 보내 줘. 쿼리로그 데이터는 **서버에서 service_role로만** 읽어서(브라우저로 그 키가 절대 안 나가게) **읽기 전용 표 + 위쪽 요약(질의 수·분기 비율·환각 건수·평균 지연·토큰 합계)**로 보여 주고, 한 줄을 누르면 **질문/답변 전문과 인용 검증 상세**를 볼 수 있게 해 줘.

> 붙이기 전 확인할 것: ① 비밀번호 없이 `/admin` 접근 → 막히는지 ② 올바른 비밀번호 → 로그 표가 뜨고 5장에서 쌓인 행이 보이는지 ③ service_role 키가 **브라우저 네트워크 탭에 안 나오는지**.

## 9. 핵심 용어 (한 줄 정의)

| 용어 | 한 줄 설명 |
|---|---|
| **색인 API 잠금** | 운영자만 쓰는 `/api/ingest`를 비밀키 헤더로 막는 것. 틀리면 **404**(존재 자체를 숨김). |
| **에러 일반화** | 내부 오류 **원문**은 서버 로그에만, 사용자에겐 "일시 오류" 같은 **일반 문구**만 보내는 것. |
| **레이트리밋** | 일정 시간에 허용하는 요청 횟수 상한. 초과 시 **429**. 서버리스에선 인스턴스별이라 완벽치 않음(경량 best-effort). |
| **감사 로그(`query_log`)** | 질문·답변·인용검증·지연·**IP**를 쌓는 운영의 눈. **지금은 비어 있음** — 이번에 실제로 채운다. |
| **IP 기반 식별** | 로그인이 없어 사용자 대신 **요청 IP**로 사용량·이상 호출을 추적. 레이트리밋과 같은 IP 소스. |
| **부팅 가드** | 필수 환경변수가 없으면 **부팅을 실패**시켜 런타임 사고를 막는 것. 지금은 일부 키가 `.optional()`이라 안 걸림. |
| **보안 헤더** | 브라우저에 안전 규칙을 알리는 응답 헤더(클릭재킹·MIME 스니핑 방지·HSTS 등). |
| **관리자 페이지** | `app/admin`의 신규 화면. 로그인 대신 **관리자 비밀번호 + service_role 서버 조회**로 보호하는 쿼리로그 뷰어. |
| **service_role(RLS 우회)** | 서버 전용 Supabase 키. 관리자 페이지가 이 키로 서버에서만 로그를 읽음(브라우저 노출 금지). |

## 10. 직접 만져보며 복습하기 (회차 후)

1. 헤더 없이 `/api/ingest` 호출 → **404**, 올바른 비밀키 헤더로는 정상 색인되는지.
2. 아주 긴 질문 / 너무 많은 턴 → **400**으로 거절되는지(3장).
3. 일부러 서버 에러를 유발 → 화면엔 **일반 문구**, 서버 로그엔 **원문**이 남는지(에러 일반화).
4. 같은 IP로 빠르게 반복 호출 → **429**가 뜨는지(4장 레이트리밋).
5. 질문 몇 개 후 DB의 `query_log`에 **행이 쌓이고** `ip`·`route`·`top_score`·`has_hallucination`·`ttft_ms`가 채워지는지(5장).
6. `OPENAI_API_KEY`를 비우고 `NODE_ENV=production`으로 빌드/부팅 → **부팅 실패**하는지(6장).
7. 비밀번호 없이 `/admin` 접근 → **차단**, 올바른 비밀번호 → 로그 표·요약이 뜨고 service_role 키가 **브라우저에 노출 안 되는지**(7장).

---

> 이 회차를 마치면 **기존 챗봇 화면은 그대로 둔 채** 프로덕션이 크게 단단해진다 — 색인 API가 닫히고, 입력·에러·요청량에 방벽이 서고, **IP 기반 운영 로그**가 비로소 쌓이며, 설정 위생이 잡히고, 운영자는 **관리자 페이지**에서 그 로그를 본다. 이 서비스는 **로그인 없이** 운영하기로 했으므로(상단 설계 결정), 책임추적은 IP로, 관리 보호는 비밀번호로 한다.
>
> **남은 후속**: ① **문서 정합** — `CLAUDE.md`·`docs/00`·`docs/07`를 no-login 기준으로 갱신(로그인 필수·RLS 권한분리 서술 수정). ② **비용 가드** — 쌓인 로그로 임계치를 정해 일·IP별 토큰 상한·차단·알림. ③ 7월 — Vercel 오픈 환경설정·관리자 통계 고도화. (로그인 게이트는 이번 결정으로 계획에서 제거됨.)
