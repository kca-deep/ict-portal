# 7회차 - 관리자 페이지: 문(로그인)부터 열고 → 별도 대시보드까지

> 이 문서는 `docs/superpowers/specs/2026-07-07-admin-auth-first-design.md`(설계 결정)의 **구현 계획**이다.
> 6회차에서 쪼갠 관리자 페이지를 **문(로그인) → 설정 청소 → 대시보드** 순으로, 처음부터 **1번부터 순차 번호**로 다시 정리했다.
> 이번 회차도 **기존 챗봇 화면(`app/page.tsx`·`components/**`)은 일절 건드리지 않는다.** 새로 만드는 것은 전부 `app/admin/**`·`app/api/admin/**`·`middleware.ts`.

> **⚠️ 전제 (6회차에서 확정)**
> 이 서비스는 **로그인 없이 운영**한다. 그래서 사용자 식별은 **요청 IP**로 하고(감사 로그), 관리자 화면만 **관리자 비밀번호 + service_role 서버 조회**로 보호한다. RLS 역할 분리는 쓰지 않는다.

| 항목 | 내용 |
|------|------|
| 날짜 | 2026-07-07 주 (이번 주) |
| 이번 주제 | **관리자 페이지 완성** — ① 관리자 비밀번호 문(로그인) ② 설정 위생 청소 ③ 별도 대시보드(쿼리로그 뷰어) |
| 선행 상태 | 6회차의 **감사 로그 적재(`query_log`, IP 기반)** 가 되어 있어야 대시보드에 실제 데이터가 뜬다. (적재 코드·마이그레이션은 진행 중) |
| 손대지 않는 것 | `app/page.tsx`, `components/**` (기존 챗봇 화면 전부) |
| 새로 만드는 것 | `app/admin/**`(로그인 폼·대시보드), `app/api/admin/**`(로그인 API), `middleware.ts`(문지기), `lib/db/query-log.ts`(조회·집계 확장) |

> **이번 회차 한 줄 요약**
> 관리자 페이지는 사실 **문(로그인)** 과 **방(대시보드)** 두 부분이다. **문을 먼저** 달아 잠금이 제대로 되는지 빈 방으로 확인하고 → 설정을 한 번에 청소하고 → 그다음 방을 **별도 대시보드**로 채운다. 제일 까다로운 인증부터 검증하고, 설정 청소(특히 `vercel.json`)를 admin 주소까지 한 번에 끝내려는 순서다.

---

## 0. 왜 이 순서인가 (가장 먼저 볼 것)

관리자 페이지를 통째로 만들지 않고 **문 → 방**으로 쪼갠 뒤, **문을 방·설정 청소보다 먼저** 만든다.

| 이유 | 내용 |
|---|---|
| **위험 선검증** | 이번에 제일 까다로운 건 인증 껍데기(비번 검증 → 서명 httpOnly 쿠키 → `/admin` 문지기 → service_role 서버 조회). 여기서 삐끗하면 뒤가 다 막히니 **빈 방이라도 문부터 뚫어** 확인한다. |
| **설정 청소를 한 번에** | 설정 청소(3~5번)의 `vercel.json`·보안 헤더는 `/admin`·`/api/admin` 주소를 반영해야 한다. 문(주소)이 먼저 있으면 **한 번에** 정리된다. 반대 순서면 나중에 되돌아와 또 손봐야 한다. |
| **눈에 보이는 산출물** | 교육 세션 특성상 초반에 "로그인 → 보호된 페이지"가 떠 흐름을 잡기 좋다. |

> **⚠️ 문을 크게 만들지 말 것 (PoC / YAGNI).** 인증은 **단일 공유 `ADMIN_PASSWORD` + 서명 httpOnly 쿠키**로 끝낸다. 회원가입·계정·비밀번호 재설정·역할 분리·소셜 로그인은 **전부 금지**. "문 먼저"가 문을 *거창하게* 만들라는 뜻이 되면 안 된다.

## 1. 이번 주 순서 (한눈에)

| 번호 | 무엇을 | 왜 이 순서인가 | 화면 |
|---|---|---|---|
| **1** | 관리자 비밀번호 + 로그인 API (비번 검증 → 쿠키) | 문의 잠금장치 뼈대 | 신규(관리자 전용) |
| **2** | 로그인 폼 + `/admin` 문지기(미들웨어) + 빈 관리자 페이지 | 문을 실제로 달고 **잠김/열림 검증** | 신규(관리자 전용) |
| **3** | 설정 청소 — 부팅 가드·보안 헤더·`vercel.json`·env | 문이 생겼으니 admin 주소까지 한 번에 위생 처리 | 무변경 |
| **4** | 쿼리로그 조회·집계 함수(service_role) | 대시보드가 읽을 데이터 통로 | 무변경 |
| **5** | **별도 대시보드** — 요약 + 로그 표 + 상세 | 문 안의 방을 채운다(운영의 눈) | 신규(관리자 전용) |

> 1·2번 = **문**, 3번 = **설정 청소**, 4·5번 = **방(대시보드)**. 기존 챗봇 화면은 처음부터 끝까지 무변경.

---

## 2. [1번] 관리자 비밀번호 + 로그인 API

### 2-1. 무엇을·왜

로그인이 없으니 관리자 화면은 **비밀번호 하나**로 지킨다. 비밀번호를 한 번 맞게 넣으면 **서명·만료가 붙은 httpOnly 쿠키**를 발급해, 이후 `/admin` 접근을 이 쿠키로 확인한다. httpOnly라 브라우저 스크립트가 쿠키를 못 읽어 탈취 위험이 낮다.

### 2-2. 해법

| 단계 | 작업 | 위치 |
|---|---|---|
| 1 | `ADMIN_PASSWORD: z.string().min(1)` (프로덕션 필수) | `lib/env.ts` |
| 2 | POST로 받은 비밀번호를 `ADMIN_PASSWORD`와 비교, 맞으면 **서명 httpOnly 쿠키** 발급(만료 포함), 틀리면 `401` | `app/api/admin/login/route.ts`(신규) |

> 쿠키 값은 추측·위조가 안 되게 **서버 비밀로 서명**(예: env 비밀 기반 HMAC)한다. 비밀번호 원문을 쿠키에 넣지 않는다.

### ▶ 사용자 프롬프트 — 1번

> 우리는 로그인 없이 서비스를 운영하지만 관리자 화면 하나는 지켜야 해. 환경변수 `ADMIN_PASSWORD`를 하나 두고, **비밀번호를 받는 로그인 API**(`app/api/admin/login`)를 만들어 줘. 비밀번호가 맞으면 **서명되고 만료가 있는 httpOnly 쿠키**를 발급하고, 틀리면 401로 돌려보내 줘. 쿠키에는 비밀번호 원문을 넣지 말고 **서버 비밀로 서명한 값**만 담아. 기존 챗봇 화면은 건드리지 마.

---

## 3. [2번] 로그인 폼 + `/admin` 문지기 + 빈 관리자 페이지

### 3-1. 무엇을·왜

문의 잠금장치(1번)를 실제 화면·경로에 연결한다. `/admin`에 들어오면 **미들웨어가 쿠키를 검사**해서, 없으면 로그인 폼으로 보낸다. 이 단계에서 **관리자 페이지 본문은 "로그인 성공"만 뜨는 빈 껍데기**로 둔다 — 방은 5번에서 채운다. 데이터가 한 줄도 없어도 **문이 제대로 잠기고 열리는지**를 지금 검증하는 게 목적이다.

### 3-2. 해법

| 단계 | 작업 | 위치 |
|---|---|---|
| 1 | 비밀번호 입력 폼(제출 → 1번 로그인 API 호출) | `app/admin/login/`(신규) |
| 2 | `/admin/*` 진입 시 쿠키 검사 → 없으면 로그인으로 | `middleware.ts` |
| 3 | 관리자 페이지 본문은 **"로그인 성공" 빈 껍데기만** | `app/admin/page.tsx`(신규) |

### 3-3. ✅ 문 검증 (데이터 0건이어도 가능)

- 비밀번호 **없이** `/admin` 접근 → **차단**(로그인 폼으로)
- **올바른** 비밀번호 → 빈 관리자 페이지로 **진입됨**
- service_role 키가 **브라우저 네트워크 탭에 나오지 않음**

### ▶ 사용자 프롬프트 — 2번

> 이제 그 잠금장치를 화면에 연결해 줘. `app/admin/login`에 **비밀번호 입력 폼**을 만들고(제출하면 방금 만든 로그인 API 호출), `middleware.ts`에서 **`/admin`으로 들어오는 요청의 쿠키를 검사**해서 없으면 로그인 폼으로 보내 줘. 관리자 페이지 본문(`app/admin/page.tsx`)은 지금은 **"로그인 성공"만 보이는 빈 화면**으로 둬 — 표는 나중에 채울 거야. 붙인 뒤 세 가지를 확인해 줘: ① 비번 없이 `/admin` → 막히는지 ② 맞는 비번 → 빈 페이지 들어가지는지 ③ service_role 키가 브라우저에 안 나오는지.

---

## 4. [3번] 설정 청소 — 부팅 가드 · 보안 헤더 · `vercel.json` · env

### 4-1. 무엇을·왜

문(admin 주소)이 생겼으니, 화면과 무관한 **설정 위생**을 한 번에 처리한다. 특히 `vercel.json`·보안 헤더가 **admin 주소까지 반영**되도록 이 시점에 정리한다.

| 항목 | 내용 |
|---|---|
| 부팅 가드 복구 | `OPENAI/ANTHROPIC/COHERE/LAW_GO_KR_API_KEY`가 `.optional()`이라 비어도 부팅됨 → **프로덕션에선 필수**로(예: `NODE_ENV==="production"`이면 필수) |
| 보안 헤더 | `next.config.ts`에 전역 헤더(`X-Frame-Options: DENY`·`X-Content-Type-Options: nosniff`·`Referrer-Policy`·HSTS). **관리자 쿠키·페이지를 깨지 않는지** 함께 확인 |
| `vercel.json` 정합 | 존재하지 않는 라우트 참조 제거 + **실재하는 `/admin`·`/api/admin` 라우트까지 한 번에** 반영 |
| env 정합 | 이번에 추가된 `ADMIN_PASSWORD`(+6회차 키들)를 `.env.local`·Vercel 양쪽에 반영 |

### 4-2. 해법

| 단계 | 작업 | 위치 |
|---|---|---|
| 1 | optional 4개 키 프로덕션 필수화(superRefine) | `lib/env.ts` |
| 2 | 전역 보안 헤더 | `next.config.ts` |
| 3 | 없는 라우트 제거 + admin 라우트 반영 | `vercel.json` |
| 4 | 신규 키를 `.env.local`/Vercel에 반영 | (배포 설정) |

### ▶ 사용자 프롬프트 — 3번

> 문이 생겼으니 설정을 한 번에 청소하자. ① 환경변수 검증에서 **LLM·임베딩·재정렬·법령 키가 비어도 부팅되는** 문제를 고쳐 **운영에선 없으면 부팅 실패**하게(로컬은 유연하게). ② Next 설정에 **기본 보안 헤더**(클릭재킹·MIME 스니핑 방지·HSTS)를 전역으로 켜 줘 — 단 관리자 쿠키·페이지가 깨지지 않는지 확인하고. ③ `vercel.json`이 **없는 API 경로**를 가리키니 정리하고, 이번에 생긴 **`/admin`·`/api/admin` 경로까지 반영**해 줘. ④ 새로 생긴 환경변수(`ADMIN_PASSWORD` 등)를 빠짐없이 넣도록 안내해 줘. 전부 화면과 무관한 설정이야.

## 5. [4번] 쿼리로그 조회·집계 함수 (service_role)

### 5-1. 무엇을·왜

대시보드(5번)가 읽을 **데이터 통로**를 먼저 만든다. 쿼리로그 조회는 **서버에서 service_role로만** 수행한다(RLS 우회, 브라우저로 키 노출 금지). 목록·집계 두 함수로 나눈다.

| 함수 | 역할 |
|---|---|
| `listQueryLogs(filter)` | 최근 N건 + 필터(기간·route·환각만·IP) |
| `queryLogStats(filter)` | 요약 집계(질의 수·분기 비율·환각 건수·평균 `total_ms`·`ttft_ms`·토큰 합계) |

> 이 파일(`lib/db/query-log.ts`)은 6회차의 **적재 헬퍼**가 이미 자리 잡은 곳이다. 여기에 **조회·집계**를 확장한다.

### 5-2. 해법

| 단계 | 작업 | 위치 |
|---|---|---|
| 1 | `listQueryLogs`·`queryLogStats`(service_role 조회) 추가 | `lib/db/query-log.ts` |

### ▶ 사용자 프롬프트 — 4번

> 대시보드가 읽을 데이터 함수를 먼저 만들어 줘. `lib/db/query-log.ts`에 **service_role로만** `query_log`를 읽는 두 함수를 추가해: 하나는 **최근 N건 + 필터(기간·분기·환각만·IP)** 목록, 하나는 **요약 집계(질의 수·분기 비율·환각 건수·평균 지연·토큰 합계)**. 이 조회는 **서버에서만** 일어나게 하고 service_role 키가 브라우저로 절대 안 나가게 해.

## 6. [5번] 별도 대시보드 — 요약 + 로그 표 + 상세

### 6-1. 무엇을·왜

2번에서 만든 빈 관리자 페이지를 **읽기 전용 대시보드**로 채운다. 운영자가 **무슨 질문이 들어오고, 어디로 분기되고, 환각·오류·지연·비용이 어떤지**를 한 화면에서 본다. 기존 챗봇 화면과 **완전히 분리된 별도 화면**이다.

### 6-2. 화면 구성 (PoC — 읽기 전용)

| 영역 | 내용 | 소스 |
|---|---|---|
| 상단 요약 | 오늘/최근 질의 수, 분기 비율(규정/법령/범위밖), 환각 건수, 평균 `total_ms`·`ttft_ms`, 토큰 합계 | `queryLogStats` |
| 로그 표 | 시각·IP·질문(요약)·route·top_score·환각 여부·지연·토큰 | `listQueryLogs` |
| 상세 보기 | 한 행 클릭 → 질문/답변 전문·인용 verdict·근거 doc_ids·law_refs | `query_log` 단건 |
| 필터 | 기간·route·환각만·IP | 쿼리 파라미터 |

### 6-3. 해법

| 단계 | 작업 | 위치 |
|---|---|---|
| 1 | 서버 컴포넌트로 요약·표·상세 렌더(4번 함수 사용) | `app/admin/page.tsx` |

### 6-4. ✅ 대시보드 검증

- 6회차에서 쌓인 `query_log` **행이 표에 보임**
- 요약(질의 수·분기 비율·환각 건수·평균 지연·토큰 합계)이 **실제 값**으로 뜸
- 한 행 클릭 → **질문/답변 전문·인용 검증 상세**가 보임

### ▶ 사용자 프롬프트 — 5번

> 이제 빈 관리자 페이지를 **별도 대시보드**로 채워 줘. 위쪽에 **요약**(질의 수·분기 비율·환각 건수·평균 지연·토큰 합계), 그 아래 **읽기 전용 로그 표**(시각·IP·질문 요약·분기·관련도·환각·지연·토큰), 한 줄을 누르면 **질문/답변 전문과 인용 검증 상세**가 뜨게. 데이터는 4번에서 만든 함수로 **서버에서 service_role로만** 읽어(브라우저로 키 안 나가게). 기간·분기·환각·IP로 거를 수 있는 간단한 필터도 넣어 줘. 붙인 뒤 6회차에서 쌓인 행이 표·요약에 실제로 뜨는지 확인해 줘.

## 7. 구현계획 (단계별) + 파일 맵

작은 것·위험 낮은 것부터. **각 단계 끝에 `pnpm build` 확인.**

| 번호 | 작업 | 손대는 파일 | 기존 화면 |
|---|---|---|---|
| **1** | 관리자 비밀번호 + 로그인 API(비번 검증 → 쿠키) | `lib/env.ts`, `app/api/admin/login/route.ts`(신규) | 무변경 |
| **2** | 로그인 폼 + `/admin` 문지기 + 빈 관리자 페이지 | `app/admin/login/`(신규), `middleware.ts`, `app/admin/page.tsx`(신규) | 신규 |
| **3** | 설정 청소(부팅 가드·보안 헤더·`vercel.json`·env) | `lib/env.ts`, `next.config.ts`, `vercel.json` | 무변경 |
| **4** | 쿼리로그 조회·집계 함수(service_role) | `lib/db/query-log.ts` | 무변경 |
| **5** | 별도 대시보드(요약·표·상세·필터) | `app/admin/page.tsx` | 신규 |

```
lib/
├─ env.ts ················ [1·3] ADMIN_PASSWORD 추가 + optional 키 production 필수화
└─ db/query-log.ts ······· [4] (확장) listQueryLogs · queryLogStats (service_role 조회)

├─ admin/login/ ·········· [2] (신규) 비밀번호 입력 폼
├─ admin/page.tsx ········ [2] 빈 껍데기 → [5] 별도 대시보드(요약·표·상세)

middleware.ts ············ [2] /admin/* 쿠키 문지기
next.config.ts ··········· [3] 전역 보안 헤더
```

## 8. 핵심 용어 (한 줄 정의)

| 용어 | 한 줄 설명 |
|---|---|
| **문(로그인)** | 관리자 비밀번호로 여닫는 잠금. 맞으면 **서명 httpOnly 쿠키** 발급. |
| **httpOnly 쿠키** | 브라우저 스크립트가 못 읽는 쿠키. 서명·만료를 붙여 위조·탈취를 막음. |
| **문지기(미들웨어)** | `/admin/*` 요청마다 쿠키를 검사해 없으면 로그인으로 보내는 것(`middleware.ts`). |
| **설정 청소** | 화면과 무관한 위생 처리 — 부팅 가드·보안 헤더·`vercel.json` 정합·env 반영. |
| **부팅 가드** | 필수 환경변수가 없으면 **부팅을 실패**시켜 런타임 사고를 막는 것. |
| **service_role(RLS 우회)** | 서버 전용 Supabase 키. 대시보드가 **서버에서만** 이 키로 로그를 읽음(브라우저 노출 금지). |
| **별도 대시보드** | 기존 챗봇 화면과 분리된 `app/admin`의 읽기 전용 화면 — 요약·로그 표·상세. |

## 9. 직접 만져보며 복습하기 (회차 후)

1. 비밀번호 **없이** `/admin` 접근 → **차단**되는지(문지기).
2. **틀린** 비밀번호 → `401`, **맞는** 비밀번호 → 빈 관리자 페이지 진입되는지(1·2번).
3. 로그인 후 새로고침해도 **쿠키로 세션이 유지**되는지, 만료 뒤엔 다시 로그인으로 가는지.
4. `OPENAI_API_KEY`를 비우고 `NODE_ENV=production`으로 빌드/부팅 → **부팅 실패**하는지(3번).
5. `vercel.json`이 **없는 경로**를 안 가리키고 `/admin`·`/api/admin`을 반영하는지(3번).
6. 대시보드에 6회차에서 쌓인 **행이 뜨고**, 요약·분기 비율·환각 건수가 **실제 값**인지(5번).
7. 대시보드 조회 시 **service_role 키가 브라우저 네트워크 탭에 안 나오는지**(4·5번).

---

> 이 회차를 마치면 **기존 챗봇 화면은 그대로 둔 채** 관리자 페이지가 완성된다 — **문(비밀번호 로그인)** 이 먼저 서고, 설정이 admin 주소까지 한 번에 청소되며, 그 문 안에 **별도 대시보드**가 채워져 운영자가 로그를 본다.
