# 2회차 - AI 챗봇 화면 만들기 (질문하면 답이 실시간으로 나오는 대화창)

| 항목 | 내용 |
|------|------|
| 날짜 | 2026-06-09 (화) |
| 이번 주제 | 사람이 질문하고 AI가 실시간으로 답하는 대화 화면(챗봇 UI) 만들기 |

> **이번 회차 한 줄 요약**
> 사용자가 질문을 입력하면, 규정을 검색해 그 내용을 근거로 AI가 답을 만들고, 그 답이 한 글자씩 화면에 차오르는 대화 화면을 만들었다. 답 아래에는 답의 근거가 된 규정 문서가 함께 표시된다.

---

## 0. 들어가기 전에

이 자료는 **바이브코딩**(개발자가 코드를 직접 타이핑하는 대신, 사람이 말로 지시하면 AI가 코드를 작성하는 방식)으로 만든 결과물을 비전공자가 이해하도록 정리한 복습 자료다. 목표는 코드를 외우는 것이 아니라 **"무엇을, 왜 만들었는가"** 를 이해하는 것이다.

이 문서에 나오는 **바이브코딩 프롬프트**(AI에게 실제로 입력하는 지시문)는 모두 `>` 인용 블록으로 표시했다. 학습자가 Claude에게 직접 입력했을 법한 문장들이다.

---

## 1. 이번에 만든 화면이 하는 일

이번에 만든 것은 사람이 질문을 입력하면 AI가 답하는 **대화 화면**이다. 한 번의 질문과 답변이 처리되는 과정을 시간 순서대로 보면 다음과 같다.

1. **질문 입력** — 사용자가 입력창에 질문을 적고 보낸다. (예: "사업비 정산 기한이 언제야?")
2. **규정 검색** — 서버가 질문과 의미가 비슷한 규정 문서를 데이터베이스에서 찾는다. 이 검색은 이미 동작한다.
3. **AI 답변 생성** — 검색으로 찾은 규정 내용을 근거로 AI(Claude)가 답을 작성한다.
4. **실시간 화면 표시** — AI가 답을 다 쓸 때까지 기다리지 않고, 답이 만들어지는 대로 글자가 화면에 차례로 나타난다.

여기서 핵심은 4번이다. 답을 다 완성한 뒤에 한꺼번에 보여주는 것이 아니라, 생성되는 즉시 조금씩 화면에 표시한다. 이렇게 답을 한 글자씩 흘려보내는 방식을 **스트리밍(streaming)** 이라고 한다.

**스트리밍이 좋은 이유**: 답이 길어도 사용자는 첫 글자가 나오는 즉시 읽기 시작할 수 있다. 답을 완성할 때까지 빈 화면을 보며 기다리지 않아도 되므로, 체감 응답 속도가 훨씬 빠르고 "멈춘 것 아닌가" 하는 불안이 없다.

> **참고**: 답변을 생성하는 AI는 Anthropic의 **Claude(claude-sonnet-4-6)** 모델이다. 같은 시스템 프롬프트(AI에게 매번 동일하게 전달하는 기본 지시문)를 반복 전송할 때 비용을 줄이는 **프롬프트 캐싱** 기능도 함께 사용한다.

## 2. 만든 기능 5가지

각 기능을 "무엇을 만들었나 / 왜 만들었나" 중심으로 설명하고, 그 기능을 만들기 위해 Claude에게 입력했을 법한 바이브코딩 프롬프트를 하나씩 붙였다.

### 기능 ① 멀티턴 대화

- **무엇**: 한 번 묻고 끝나는 것이 아니라, 앞에서 주고받은 대화를 이어서 답한다. 예를 들어 "신청 기간 알려줘"라고 묻고 답을 받은 뒤 "그럼 서류는?"이라고 물으면, AI는 "그럼"이 앞선 신청 관련 질문의 연장임을 이해한다.
- **왜**: 사용자가 매번 질문에 모든 배경을 다시 적지 않아도 자연스럽게 대화를 이어갈 수 있게 하기 위해서다.
- **동작 방식**: 새 질문을 보낼 때마다 지금까지의 대화 전체를 함께 보낸다. AI는 매번 대화 전체를 처음부터 다시 읽어 맥락을 파악한다. 즉 AI가 이전 대화를 따로 기억하고 있는 것이 아니라, 매 요청마다 전체 대화 내용을 다시 받아 읽는다. 그래서 대화가 길어질수록 보내는 양도 늘어난다.

### ▶ 사용자 프롬프트 — 1

> 사용자가 새 메시지를 보낼 때, 그 메시지 하나만 보내지 말고 지금까지의 대화 전체(이전 질문과 답변 모두)를 함께 AI에 전달해서, AI가 앞선 맥락을 이어 답하게 해줘.

### 기능 ② 스트리밍

- **무엇**: 질문을 보내면 답이 준비되는 대로 글자가 차례로 화면에 나타난다. 답을 기다리는 동안에는 입력 중임을 알리는 표시가 깜빡인다.
- **왜**: 답이 길어도 사용자가 첫 글자부터 바로 읽을 수 있어 기다리는 느낌이 줄어든다.

### ▶ 사용자 프롬프트 — 2

> AI의 답변을 한 번에 다 받아서 표시하지 말고, 생성되는 대로 글자가 화면에 실시간으로 차오르도록 스트리밍 방식으로 연결해줘. 답을 기다리는 동안에는 입력 중 표시를 보여줘.

### 기능 ③ 마크다운 렌더

먼저 용어부터 정리한다.
- **마크다운**: 제목, 번호 목록, 표, 굵은 글씨 같은 서식을 간단한 기호로 표현하는 글쓰기 규칙이다. AI 답변에는 이런 서식이 들어 있다.
- **렌더링**: 서식 기호가 섞인 글자 데이터를, 사람이 보기 좋은 화면(표는 표 모양으로, 목록은 들여쓰기로)으로 그려내는 것이다.

- **무엇**: AI 답변에 들어 있는 제목, 목록, 표, 굵은 글씨를 보기 좋게 그려서 표시한다.
- **왜**: 서식 기호가 그대로 노출되면 읽기 어렵기 때문이다.
- **까다로운 점 1**: 답이 한 글자씩 들어오는 도중에는 서식이 항상 미완성 상태다. 예를 들어 굵게 표시를 여는 기호는 도착했지만 닫는 기호는 아직 안 온 순간이 있다. 이런 미완성 서식이 들어와도 화면이 깨지지 않도록 그려주는 `streamdown` 도구를 사용했다.
- **까다로운 점 2**: 한국어에서는 굵게 표시한 단어 바로 뒤에 조사("한", "를", "에" 등)가 붙으면 서식이 제대로 적용되지 않는 문제가 있다. 이 경우에도 서식이 깨지지 않도록 처리했다.

### ▶ 사용자 프롬프트 — 3

> AI 답변의 마크다운(제목, 목록, 표, 굵은 글씨)을 화면에 보기 좋게 렌더링해줘. 단, 답이 한 글자씩 들어오는 중이라 서식이 미완성인 순간에도 화면이 깨지지 않게 해줘. 그리고 굵은 글씨 바로 뒤에 한국어 조사가 붙으면 서식이 깨지는 문제도 함께 고쳐줘.

### 기능 ④ 스크롤 제어

- **무엇**: 답이 나오는 동안 화면이 자동으로 맨 아래를 따라 내려가되, 사용자가 직접 위로 올리면 따라가기를 멈추고, 사용자가 다시 맨 아래로 내리면 따라가기를 다시 켠다.
- **왜**: 답이 계속 나오는 동안 화면이 무조건 맨 아래를 따라가면, 사용자가 위로 올려 이전 내용을 읽으려 할 때 새 글자가 나올 때마다 도로 아래로 끌려가 읽을 수가 없다. 사용자의 스크롤 의도를 존중하기 위해 이 동작을 넣었다.

### ▶ 사용자 프롬프트 — 4

> 답이 스트리밍되는 동안 화면이 자동으로 맨 아래를 따라가게 해줘. 단, 사용자가 위로 스크롤하면 자동 따라가기를 멈추고, 사용자가 다시 맨 아래까지 내리면 자동 따라가기를 다시 켜줘.

### 기능 ⑤ 근거(참조 문서) 펼침

먼저 용어를 정리한다.
- **환각**: AI가 실제로는 없는 내용을 사실인 것처럼 지어내는 현상이다.

- **무엇**: AI 답변 아래에 "참조 문서" 카드가 붙는다. AI가 답을 만들 때 실제로 참고한 규정들이다. 평소에는 접혀 있고, 누르면 전체 내용이 펼쳐진다.
- **왜**: 규정·법령 챗봇은 답이 어떤 조항을 근거로 한 것인지 보여줘야 신뢰할 수 있다. 사용자가 근거 문서를 직접 펼쳐 확인하면, AI가 없는 내용을 지어낸 환각인지 아닌지 스스로 검증할 수 있다.

### ▶ 사용자 프롬프트 — 5

> 각 AI 답변 아래에, 그 답을 만들 때 검색해서 참고한 규정 문서들을 "참조 문서" 카드로 표시해줘. 평소에는 접혀 있다가 누르면 전체 내용이 펼쳐지게 해줘.

## 3. 주요 결정과 이유

바이브코딩으로 만들더라도, 중요한 갈림길에서는 방향을 정해야 한다. 이번에 내린 결정들은 다음과 같다.

| 결정 사항 | 선택 | 이유 |
|---|---|---|
| 답을 한 번에 줄지, 흘려보낼지 | 흘려보내기(스트리밍) | 사용자가 첫 글자부터 바로 읽을 수 있어 기다리는 느낌이 줄어든다. 긴 답일수록 효과가 크다. |
| 화면과 서버 사이 통신 방식 | 필요한 만큼만 단순하게 직접 구현 | 복잡한 외부 틀에 얽매이지 않고, 스트리밍에 필요한 최소한의 기능만 단순하게 구현했다. |
| 마크다운 렌더 도구 | `streamdown` | 답이 스트리밍으로 들어오는 도중의 미완성 서식도 깨지지 않게 그려주기 때문이다. |
| 답변의 근거 표시 여부 | 답마다 참조 문서 첨부 | 규정 챗봇은 근거 없는 답이 위험하다. 근거를 함께 보여줘야 사용자가 검증할 수 있다. |

## 4. 현재 상태

- **대화 화면(UI)**: 완성되어 동작한다. 멀티턴 대화, 스트리밍 답변, 마크다운 렌더, 스크롤 제어, 근거 표시가 모두 동작한다.
- **AI 답변 생성**: 동작한다. Claude(claude-sonnet-4-6)가 실제로 답을 생성한다.
- **규정 검색**: 동작한다. 질문과 의미가 비슷한 규정을 찾아 그 결과를 답의 근거로 사용한다. 이 검색은 **OpenAI**의 임베딩 도구 `text-embedding-3-small`(1024차원)을 사용한다. 이 임베딩 도구는 바꾸지 않는다.

아직 연결하지 않은 부분은 다음 두 가지이며, 현재 미연결 상태다.

- **Cohere Rerank(재정렬)**: 검색 결과를 한 번 더 정밀하게 거르는 단계다. 코드(`lib/ai/rerank.ts`)는 작성되어 있으나 아직 챗 흐름에 연결되어 있지 않다.
  - 주의: Rerank는 임베딩을 교체하는 것이 아니다. 임베딩(OpenAI)은 그대로 두고, 검색 뒤에 거름망 한 단계를 추가하는 별도 단계다. 따라서 문서를 다시 색인할(재색인) 필요가 없다.
- **법령 실시간 조회(법제처 MCP)**: 자주 바뀌는 법령을 공식 출처에서 실시간으로 받아 근거로 쓰는 기능이다. 현재 미연결 상태다.

## 5. RAG와 Rerank의 구조 차이

먼저 용어를 정리한다.
- **임베딩**: 문서나 질문을 컴퓨터가 의미로 비교할 수 있도록 숫자(벡터)로 바꾼 것이다. 검색의 핵심 재료다.
- **RAG**: 질문과 관련된 자료를 검색해서(retrieve) 찾고, 그 자료를 근거로 AI가 답을 생성하는(generate) 방식이다.
- **Rerank(재정렬)**: 검색으로 넓게 추린 여러 후보 문서를, 질문과 하나씩 1:1로 정밀 비교해 더 정확한 것만 다시 골라내는 단계다.

**RAG의 검색 단계**는 임베딩을 이용해 질문과 의미가 비슷한 문서를 넓게 찾는다. 이 방식은 매우 빠르지만, "대충 비슷한" 문서까지 섞여 들어와 정밀도가 떨어진다.

**Rerank 단계**는 그 후보 문서들을 질문과 1:1로 직접 맞대어 비교한다. 정밀도가 높아 진짜 관련 있는 문서만 남길 수 있지만, 한 건씩 비교하므로 느리고 비용이 든다.

그래서 두 단계로 나눈다. 그 이유를 정리하면 다음과 같다.

| 단계 | 성격 | 한계 |
|---|---|---|
| **임베딩 검색 (RAG의 검색)** | 매우 빠르다. 수많은 문서도 순식간에 훑는다. | 정밀도가 낮다. 대충 비슷한 문서까지 섞인다. |
| **Rerank (재정렬)** | 매우 정밀하다. 질문과 문서를 1:1로 직접 비교한다. | 느리고 비용이 든다. 수많은 문서를 전부 비교할 수는 없다. |

전체 문서를 처음부터 Rerank로 비교하면 너무 느리고, 빠른 검색만 믿으면 엉뚱한 문서가 섞인다. 그래서 **빠른 임베딩 검색으로 후보를 넓게 추린 뒤, 정밀한 Rerank로 그 후보 중에서만 좁게 엄선**하는 2단계 구조를 쓴다. 두 단계를 거치면 AI가 받는 자료의 정확도가 높아지고, 핵심 규정이 빠지거나 엉뚱한 자료가 섞일 확률이 줄어든다.

규정·법령처럼 정확한 한 조항을 찾는 것이 중요한 분야일수록 이 두 단계 구조의 효과가 크다. 단, 앞서 적었듯이 Rerank는 현재 미연결 상태다.

## 6. 핵심 용어

| 용어 | 한 줄 정의 |
|---|---|
| **멀티턴** | 앞에서 주고받은 대화를 이어가는 대화 방식. 새 질문마다 대화 전체를 다시 보낸다. |
| **스트리밍** | 답을 다 만들 때까지 기다리지 않고, 생성되는 대로 한 글자씩 화면에 흘려보내는 것. |
| **마크다운** | 제목, 목록, 표, 굵은 글씨 같은 서식을 기호로 표현하는 글쓰기 규칙. |
| **렌더링** | 서식 기호가 섞인 글자 데이터를 사람이 보기 좋은 화면으로 그려내는 것. |
| **RAG** | 질문과 관련된 자료를 검색해 찾고, 그 자료를 근거로 AI가 답을 생성하는 방식. |
| **근거(sources)** | AI가 답을 만들 때 실제로 참고한 규정 문서들. 답 아래에 표시된다. |
| **임베딩** | 문서나 질문을 컴퓨터가 의미로 비교할 수 있도록 숫자로 바꾼 것. |
| **Rerank(재정렬)** | 검색으로 넓게 추린 후보를 질문과 1:1로 정밀 비교해 다시 골라내는 단계. |
| **환각** | AI가 실제로는 없는 내용을 사실인 것처럼 지어내는 현상. |
| **시스템 프롬프트** | AI에게 매번 동일하게 전달하는 기본 지시문. AI의 역할과 규칙을 정한다. |
| **프롬프트 캐싱** | 같은 시스템 프롬프트를 반복 전송할 때 비용을 줄이는 기능. |

## 7. 직접 만져보며 복습

화면을 띄워(`pnpm dev`) 직접 확인해보면 기억에 더 잘 남는다. 다음 항목을 점검해보자.

1. 질문을 길게 하나 던지고, 답이 한 글자씩 차오르는지 본다. (스트리밍)
2. 답이 나오는 도중에 화면을 위로 올려보고, 도로 아래로 끌려가지 않는지 확인한다. 그다음 다시 맨 아래로 내려 자동 따라가기가 켜지는지 확인한다. (스크롤 제어)
3. 답 아래의 참조 문서 카드를 펼쳤다 접어본다. (근거 표시)
4. 표나 목록이 들어간 답을 받아 서식이 보기 좋게 그려지는지 본다. (마크다운 렌더)
5. 한 질문에 답을 받은 뒤 "그럼 그건?"처럼 이어지는 짧은 질문을 던져, 앞 대화를 이어 답하는지 확인한다. (멀티턴)
