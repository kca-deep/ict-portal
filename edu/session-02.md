## 0. 바이브코딩이 뭐고, 이 문서는 왜 코드가 없나

이 프로젝트는 **바이브코딩(vibe coding)** 방식으로 만든다.
= 내가 코드를 직접 타이핑하는 게 아니라, **"이런 걸 만들어줘"라고 말로 시키면 AI(Claude)가 코드를 짜주는** 방식이다.

그래서 이 복습 자료의 목표는 "코드를 외우는 것"이 아니라:

1. **내가 무엇을 만들었는지** 큰 그림으로 이해하기
2. **왜 그렇게 만들었는지** 이유를 알기 (나중에 비슷한 결정을 할 때 판단 근거)
3. **다음에 뭘 시켜야 하는지** 감 잡기

코드는 Claude가 관리하니, 우리는 **"무엇을·왜"** 에만 집중한다.

## 1. 이번에 만든 화면이 하는 일 (큰 그림)

식당에 비유하면 이렇다.

```
손님(사용자)  ──질문──►  점원(화면)  ──주문전달──►  주방(서버)
                                                       │
                                          ┌────────────┴────────────┐
                                          │ ① 창고에서 재료 찾기      │  = 규정 문서 검색
                                          │ ② 요리사가 요리하기       │  = AI(Claude)가 답변 작성
                                          └────────────┬────────────┘
                                                       │
손님 ◄──접시 나오는 대로 바로바로──  점원  ◄──완성되는 대로 한 입씩──  주방
```

핵심은 **"완성될 때까지 기다렸다 한 번에 주는 게 아니라, 만들어지는 대로 바로바로 보여준다"** 는 것이다.
- ❌ 옛날 방식: AI가 답을 다 쓸 때까지 빈 화면 → 다 되면 한꺼번에 툭.
- ✅ 이번 방식: AI가 한 문장 쓰면 바로 화면에, 다음 문장 쓰면 또 바로. **타이핑되는 느낌.**

이걸 **스트리밍(streaming)** 이라고 부른다. 사용자 체감 속도가 훨씬 빠르다.

## 2. 만든 기능 5가지 (하나씩 쉽게)

### 기능 ① 여러 번 주고받는 대화 (멀티턴)

- 한 번 묻고 끝이 아니라, **앞서 한 대화를 기억하고 이어서** 답한다.
- 예: "신청 기간 알려줘" → (답변) → "그럼 서류는?" 이라고 물으면, AI가 "그럼"이 신청 관련 질문임을 안다.
- **어떻게?** 새 질문을 보낼 때마다 **지금까지의 대화 전체를 같이 보낸다.** AI는 매번 처음부터 다시 읽고 맥락을 파악한다.
- 💡 알아둘 점: AI는 사실 "기억"이 없다. 매번 대화 내용을 통째로 다시 받아서 읽는 것뿐. 그래서 대화가 길어지면 보내는 양도 늘어난다.

### 기능 ② 답이 실시간으로 흘러나오기 (스트리밍)

- 질문을 보내면 즉시 **"입력 중..." 점 3개** 가 깜빡이고, 답이 준비되는 대로 글자가 차오른다.
- **왜 좋은가?** 답이 길어도 사용자는 "멈춘 거 아냐?" 하는 불안 없이, 첫 글자부터 읽기 시작할 수 있다.

### 기능 ③ 답을 예쁘게 정리해서 보여주기 (마크다운)

- AI 답변에는 **제목, 번호 목록, 표, 굵은 글씨** 같은 서식이 들어간다.
- 이걸 그냥 글자로 두지 않고 **보기 좋게 렌더링**한다. (표는 표 모양으로, 목록은 들여쓰기로)
- **까다로운 점 하나**: 답이 한 글자씩 들어오는 중에는 서식이 **항상 미완성**이다. (예: `**굵게` 인데 닫는 표시가 아직 안 옴)
  - 그래서 **미완성 서식도 안 깨지게** 그려주는 특별한 도구(`streamdown`)를 썼다.
- **한국어 특유 문제도 해결**: `**중요**한` 처럼 굵게 표시 바로 뒤에 한글 조사("한", "를", "에")가 붙으면 서식이 안 먹는 버그가 있다. 이걸 잡아주는 장치를 추가했다.

### 기능 ④ 스크롤이 똑똑하게 동작 (스크롤 제어)

- **문제 상황**: 답이 줄줄 나오는 동안 화면은 계속 맨 아래로 따라 내려간다. 그런데 사용자가 **위로 올려서 이전 내용을 읽으려 하면**, 새 글자가 나올 때마다 도로 아래로 홱 끌려간다. → 짜증.
- **해결**: 
  - 사용자가 **위로 스크롤하는 순간** "아, 지금 위를 보고 싶구나" 하고 **자동 따라가기를 멈춘다.**
  - 다시 **맨 아래까지 내리면** "이제 최신 답을 보고 싶구나" 하고 **따라가기를 켠다.**
- 💡 이건 작지만 체감이 큰 UX 디테일이다. 좋은 챗봇은 다 이렇게 동작한다.

### 기능 ⑤ 답의 근거를 함께 보여주기 (참조 문서 펼침)

- AI 답변 아래에 **"참조 문서 N건"** 카드가 붙는다. 답할 때 실제로 본 규정들이다.
- 평소엔 **한 줄 미리보기**로 접혀 있고, 누르면 **전체 내용이 펼쳐진다.**
- **왜 중요한가?** 규정·법령 챗봇은 "그냥 믿어"가 아니라 **"이 조항을 근거로 답했다"** 를 보여줘야 신뢰가 생긴다. 환각(없는 말 지어내기)을 사용자가 직접 검증할 수 있게 하는 장치.

## 3. 알아두면 좋은 "왜 이렇게 했나" 결정들

바이브코딩이라도, 중요한 갈림길에서는 방향을 정해야 한다. 이번에 내린 결정들:

| 갈림길 | 선택 | 쉬운 이유 |
|---|---|---|
| 답을 한 번에? 흘려보내기? | **흘려보내기(스트리밍)** | 사용자가 덜 기다린 느낌. 긴 답일수록 효과 큼. |
| 통신 방식 | **단순한 방식 직접 구현** | 남이 만든 복잡한 틀에 얽매이지 않고, 우리에게 필요한 만큼만 단순하게. |
| 마크다운 그리는 도구 | **`streamdown`** | 타이핑 도중 미완성 서식도 안 깨지게 그려주는 도구라서. |
| 근거 표시 | **답마다 참조 문서 첨부** | 규정 챗봇은 신뢰가 생명. 근거 없는 답은 위험. |

이 표만 기억해도 "내가 왜 이런 챗봇을 만들었지?"에 답할 수 있다.

## 5. "RAG만" vs "RAG + 재정렬(Rerank)" — 구조 차이

위에서 "검색 솜씨를 업그레이드한다"고 했는데, 그 업그레이드의 정체가 바로 **Rerank(재정렬)** 다.
둘이 구조적으로 어떻게 다른지 쉽게 보자.

### 한 장 비유: 도서관에서 자료 찾기

내가 "사업비 정산 기한"을 알고 싶어 도서관에 갔다고 하자.

**방법 A — RAG만 (검색 한 번으로 끝)**
```
질문 ──► [기계 검색대] 키워드로 비슷해 보이는 책 8권 쭉 뽑음 ──► 그대로 요리사(AI)에게
```
- 기계가 **빠르게, 대충** 비슷한 걸 뽑는다.
- 8권 중 진짜 핵심은 5등쯤에 있고, 1~2등은 살짝 빗나간 책일 수 있다.
- 그래도 일단 AI에게 다 넘긴다.

**방법 B — RAG + 재정렬 (검색 후 사서가 한 번 더 거름)**
```
질문 ──► [기계 검색대] 일단 넉넉히 30권 뽑음
                          │
                          ▼
        [사서가 30권을 한 권씩 펼쳐] 질문과 정말 맞는지 꼼꼼히 비교
                          │
                          ▼
              가장 잘 맞는 8권만 골라 순서대로 ──► 요리사(AI)에게
```
- 1단계: 기계가 **빠르고 넓게** 후보를 많이(30권) 모은다.
- 2단계: 사서(=Rerank)가 **느리지만 정밀하게**, 질문과 각 책을 1:1로 비교해 진짜 좋은 8권을 다시 줄 세운다.
- AI는 **엄선된 8권**만 받는다.

### 왜 두 단계로 나누나? (핵심)

| 도구 | 성격 | 한계 |
|---|---|---|
| **기계 검색대 (임베딩 검색)** | 아주 빠름. 수만 건도 순식간에 훑음. | 정밀도가 떨어짐. "대충 비슷한 것"까지 섞임. |
| **사서 (Rerank)** | 아주 정밀. 질문과 문서를 직접 맞대봄. | 느리고 비쌈. 수만 건을 다 못 봄. |

→ 그래서 **"빠른 검색으로 넓게 추린 뒤(30건), 정밀한 재정렬로 좁게 엄선(8건)"** 하는 2단계가 정석이다.
처음부터 사서한테 수만 권을 다 검토시킬 수 없고(너무 느림), 기계 검색만 믿으면 엉뚱한 게 섞인다(부정확).

### 결과가 어떻게 달라지나

| | RAG만 | RAG + Rerank |
|---|---|---|
| AI가 받는 자료 | 대충 관련된 8건 | **정밀하게 엄선된 8건** |
| 핵심 규정이 빠질 확률 | 높음 | 낮음 |
| 엉뚱한 자료가 섞일 확률 | 높음 | 낮음 |
| 답변 정확도 | 보통 | **더 높음** |
| 속도/비용 | 빠르고 쌈 | 살짝 느리고 비쌈 |
| 들어가는 도구 | 검색만 | 검색 + **Rerank** |

> 한 줄 정리: **RAG = 넓게 한 번 검색. RAG+Rerank = 넓게 검색한 뒤 한 번 더 정밀하게 거름.**
> 규정·법령처럼 **"정확한 한 조항"이 중요한** 분야일수록 Rerank의 효과가 크다.

### 우리 프로젝트는?

- **목표는 RAG + Rerank** (정확도가 생명인 규정 챗봇이므로).
- Rerank 도구로는 **Cohere `rerank`** 를 쓸 예정 → **3회차에서 실제로 연결**한다.
- 즉 지금은 "기계 검색까지", 다음 회차에 "사서(재정렬)까지" 붙이는 셈이다.

## 6. 핵심 용어 9개 (이것만 알면 됨)

| 용어 | 한 줄 설명 |
|---|---|
| **멀티턴** | 앞 대화를 기억하며 이어가는 대화. (실은 매번 전체를 다시 보냄) |
| **스트리밍** | 답을 다 만들 때까지 기다리지 않고, 만들어지는 대로 흘려보내기. |
| **마크다운** | 제목·목록·표·굵은 글씨 같은 서식. AI 답변을 보기 좋게 만듦. |
| **렌더링** | 글자 데이터를 사람이 보기 좋은 화면으로 그려내는 것. |
| **RAG** | "검색해서(retrieve) 찾은 자료를 근거로 답(generate)하기." 우리 챗봇의 핵심 방식. |
| **참조/근거(sources)** | AI가 답할 때 실제로 본 규정 문서들. 답 아래에 표시. |
| **임베딩** | 문서를 컴퓨터가 의미로 비교할 수 있는 숫자로 바꾼 것. (검색의 핵심 재료) |
| **Rerank(재정렬)** | 검색으로 넓게 추린 후보를, 질문과 1:1로 정밀 비교해 다시 줄 세우는 것. |
| **UI** | 사용자가 보고 만지는 화면. 이번 회차의 주인공. |

## 7. 다음에 Claude에게 뭘 시킬까 (3회차 예고)

이번엔 **화면과 대화 방식**을 완성했으니, 다음은 **검색을 진짜 똑똑하게** 만든다.

1. **검색 도구를 Cohere로 교체** — 한국어 규정 검색이 훨씬 정확해진다.
   - ⚠️ 주의: 문서를 넣을 때 쓴 도구와, 질문을 검색할 때 쓰는 도구는 **반드시 같아야** 한다. (안 그러면 검색이 헛돈다 — 1회차에서 배운 "짝 맞추기" 규칙)
2. **검색 결과 다듬기(재정렬)** — 일단 많이 찾은 뒤, 정말 관련 있는 것 위주로 다시 줄 세우기.
3. **근거 검증** — 답에 적힌 근거가 실제 참조 문서와 맞는지 확인.

> 한 줄로: **이번 회차 = 멋진 식당을 다 차렸다. 다음 회차 = 창고 정리 솜씨를 키워 더 좋은 재료를 빨리 찾는다.**

## 부록. 직접 만져보며 복습하기

말로만 읽지 말고 `pnpm dev`로 띄워서 직접 해보면 머리에 남는다.

1. 질문을 길게 하나 던져보고 **답이 한 글자씩 차오르는 것**을 관찰하기 (= 스트리밍).
2. 답이 나오는 **도중에 화면을 위로 올려보기** → 도로 안 내려가는지 확인. 다시 맨 아래로 내리면 따라가기 켜지는지 확인 (= 스크롤 제어).
3. 답 아래 **참조 문서 카드를 펼쳤다 접어보기** (= 근거 표시).
4. 표나 목록이 들어간 답을 받아 **서식이 예쁘게 그려지는지** 보기 (= 마크다운 렌더).
