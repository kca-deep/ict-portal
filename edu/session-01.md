| 항목 | 내용 |
|------|------|
| 날짜 | 2026-05-27 (수, KST) |
| 주제 | 규정 PDF를 컴퓨터가 의미로 찾을 수 있는 데이터로 만들어 데이터베이스에 적재 |

> **한 줄 요약**
> 규정 PDF를 텍스트로 풀고, 그 텍스트를 숫자(임베딩)로 바꿔 데이터베이스에 넣는다. 이렇게 넣어두면 단어가 똑같지 않아도 의미가 가까운 조항을 찾아낼 수 있다.

---

## 1. 바이브코딩이란 무엇인가

**바이브코딩(vibe coding)** = 내가 코드를 직접 타이핑하지 않고, "이런 걸 만들어줘"라고 말로 시키면 AI(Claude Code)가 코드를 대신 짜주는 방식이다.

그래서 이 복습 자료는 코드를 외우기 위한 것이 아니다. 목표는 세 가지다. **무엇을** 만들었는지, **왜** 그렇게 만들었는지, 그리고 비슷한 작업을 할 때 **Claude에게 무엇을 시키면 되는지** 감을 잡는 것이다. 그래서 이 문서에는 코드가 거의 없고, 대신 학습자가 Claude에게 실제로 입력했을 법한 지시문이 인용문(`>`)으로 들어 있다. 그 지시문의 말투와 흐름을 익히는 것이 핵심이다.

작업 순서는 시간순이다. 준비 → 만들기 → 확인의 순서로 따라가면 된다.

## 2. 준비물과 환경 (A)

먼저 손에 들고 있어야 할 도구를 확인한다.

- **Node.js**: 자바스크립트 코드를 컴퓨터에서 실행해 주는 프로그램.
- **pnpm**: Node.js 프로젝트가 쓰는 부품(라이브러리)을 받아오고 스크립트를 실행하는 도구.
- **Claude Code**: 말로 시키면 코드를 짜주는 AI 도구.
- **Supabase CLI**: Supabase(데이터베이스)를 명령어로 다루는 도구. `CLI`는 명령어를 직접 입력해 쓰는 프로그램을 뜻한다.

설치 여부는 다음 셸 명령으로 확인한다. 셸은 명령어를 타이핑해 실행하는 검은 화면을 말한다.

```bash
node -v
pnpm -v
claude --version
supabase --version
```

설치 확인과 안내는 Claude에게 맡길 수 있다.

### ▶ 사용자 프롬프트 — 2장 (준비물 확인)

> 코드를 실행하는 도구(Node), 부품을 받아오는 도구(pnpm), 데이터베이스를 명령으로 다루는 도구(supabase)가 내 컴퓨터에 깔려 있는지 버전을 확인해 줄래? 빠진 게 있으면 Windows에서 어떻게 까는지 알려 줘.

이와 함께 두 가지를 준비했다. 첫째, **Supabase MCP** 인증이다. MCP는 Claude가 외부 도구(여기서는 Supabase)에 직접 접속해 조회·작업하게 해 주는 연결 통로다. 둘째, **OpenAI API 키** 발급이다. 임베딩을 만들 때 OpenAI 서비스를 호출해야 하므로 그 사용 열쇠가 필요하다.

## 3. Supabase 프로젝트와 `.env.local` (B)

**Supabase** = 클라우드에 있는 데이터베이스. 회원가입하면 바로 쓸 수 있다.

Supabase 사이트에서 클라우드 프로젝트를 새로 만들었다. 그다음 비밀 키와 설정값을 코드에 직접 적지 않고 `.env.local`이라는 파일에 모아 두었다. `.env.local`은 비밀값을 담아 두는 설정 파일이고, 코드 바깥에 따로 둔다.

여기에 적은 값은 크게 두 묶음이다.

**Supabase 접속 키 3개**

| 키 | 용도 |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | 내 데이터베이스 주소 |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | 화면(클라이언트)에서 쓰는 제한된 키 |
| `SUPABASE_SERVICE_ROLE_KEY` | 서버·스크립트 전용 권한 키. 화면 코드에는 절대 넣지 않는다 |

`service_role`은 데이터베이스에 무엇이든 쓸 수 있는 강한 권한이다. 그래서 사용자 화면에서 돌아가는 코드에는 넣지 않고, 서버나 내가 돌리는 스크립트에서만 쓴다.

**OpenAI 임베딩 설정**

```env
OPENAI_API_KEY=sk-...
EMBEDDING_MODEL=text-embedding-3-small
EMBEDDING_DIMENSIONS=1024
```

이 세 값은 실제 코드가 기대하는 값과 정확히 일치하는 것을 확인했다. 즉 이 프로젝트의 임베딩은 OpenAI의 `text-embedding-3-small` 모델로, 1024차원으로 만든다.

`.env.local`에 들어가는 전체 키 목록은 `.env.example` 파일을 그대로 복사한 뒤 빈칸을 내 값으로 채우면 된다. 모든 키를 여기 나열하지는 않는다.

## 4. 테이블 만들기 (C)

**테이블** = 데이터를 행과 열로 담는 표. 규정 문서를 저장할 `documents` 테이블이 여기에 해당한다.

테이블은 **마이그레이션**으로 만든다. 마이그레이션은 "데이터베이스 구조를 이렇게 바꿔라"라고 적어 둔 변경 지시 파일이다. 이 파일을 데이터베이스에 적용하면 그 안에 적힌 대로 테이블이 생긴다.

적용 명령은 Supabase CLI의 `supabase db push`다. 이 명령은 마이그레이션 파일을 실제 데이터베이스에 반영한다. 이번에는 `documents` 테이블과 함께 **vector(벡터) 확장**도 켰다. 벡터는 임베딩(숫자 목록)을 저장하고 비교할 수 있게 해 주는 기능이고, 확장은 데이터베이스에 추가로 켜는 기능 묶음을 뜻한다.

### ▶ 사용자 프롬프트 — 4장 (테이블 만들기)

> 데이터베이스 구조 바꾸라고 적어 둔 변경 지시를 실제 데이터베이스에 적용해 줘. 다 되면 규정을 담을 `documents`라는 표가 잘 생겼는지, 그리고 임베딩을 저장·검색하는 벡터 확장이 켜졌는지 보여 줘.

적용 결과는 Supabase MCP로 확인했다. 테이블 구조와 확장 설치 여부를 조회해서 의도대로 들어갔는지 눈으로 점검한 것이다. 정리하면, 테이블·구조를 **만드는** 일은 CLI의 `supabase db push`(또는 Supabase MCP)로 하고, 만들어진 결과를 **점검·조회**하는 일은 Supabase MCP나 `/supabase` 스킬로 한다.

명령 도중 에러가 나면 화면에 찍힌 로그를 그대로 복사해 다시 물으면 된다.

### ▶ 사용자 프롬프트 — 4장 (에러가 났을 때)

> 변경 지시를 적용하다가 이런 에러가 났어: [에러 로그 붙여넣기]. 왜 그런지랑 다음에 뭘 하면 되는지 알려 줄래?

## 5. 매뉴얼 PDF를 텍스트로 풀고 documents에 색인하기 (D, E, F)

### 5-1. PDF를 텍스트로 풀기 (D)

검색 대상 매뉴얼 PDF를 `data/manuals/` 폴더에 넣었다. PDF는 글자가 그림처럼 박혀 있어 그대로는 검색에 쓸 수 없다. 그래서 텍스트로 풀어내야 한다. 이 변환 작업을 **파싱**이라고 한다.

여기서는 **kordoc MCP**를 썼다. 한국어 PDF를 마크다운 텍스트로 바꿔 주는 도구다. 마크다운은 제목·표 같은 구조를 글자 기호로 표현한 단순 텍스트 형식이다. 변환 결과는 `data/manuals/parsed/`에 저장했다.

### ▶ 사용자 프롬프트 — 5-1 (PDF를 텍스트로 풀기)

> `data/manuals/` 안에 있는 매뉴얼 PDF들을 검색에 쓸 수 있는 텍스트로 풀어서 `data/manuals/parsed/`에 저장해 줘. 표가 깨지지 않게 해 주고, 파일마다 글자 수를 한 줄씩 알려 줘.

### 5-2. 색인 스크립트 만들기 (E)

이제 풀어낸 텍스트를 데이터베이스에 넣는다. 문서를 임베딩해서 미리 데이터베이스에 넣어 두는 일을 **색인**이라고 한다. 색인은 CLI나 스킬이 아니라 코드로 한다. Claude에게 `ingest-manuals.ts`라는 색인 스크립트를 만들게 했다.

이 스크립트가 하는 일은 순서대로 이렇다. 먼저 변환된 마크다운을 일정 크기로 자른다(이 자르기를 **청킹**이라고 한다. 긴 글을 한 번에 임베딩할 수 없어 적당한 조각으로 나누는 것이다). 다음으로 각 조각을 OpenAI 임베딩(1024차원)으로 바꾼다. 마지막으로 그 조각과 임베딩을 `documents` 테이블에 INSERT(추가)한다. 이 INSERT는 `service_role` 키를 쓰는 supabase-js 클라이언트가 수행한다. supabase-js는 코드에서 Supabase에 접속하는 부품이다.

### ▶ 사용자 프롬프트 — 5-2 (색인 스크립트 만들기)

> 풀어낸 텍스트 파일들을 적당한 크기 조각으로 자른 다음, 각 조각을 임베딩(1024차원)으로 바꿔서 `documents` 표에 넣는 스크립트를 만들어 줘. 어디까지 했는지 진행 상황을 화면에 찍어 주고, 데이터베이스에 무엇이든 쓸 수 있는 강한 권한 키는 이 스크립트 안에서만 쓰게 해 줘.

스크립트는 `pnpm tsx`로 실행한다. `tsx`는 타입스크립트 코드를 바로 실행해 주는 도구다.

```bash
pnpm tsx ingest-manuals.ts
```

### 5-3. 결과 확인 (F)

적재가 끝나면 Supabase MCP로 몇 건이 들어갔는지, 샘플이 제대로 들어갔는지 확인했다. 단어(키워드)로 찾는 검색도 동작하는지 함께 점검했다.

### ▶ 사용자 프롬프트 — 5-3 (결과 확인)

> `documents` 표에 몇 건 들어갔는지 세어 주고, 방금 넣은 조각 3건의 제목과 앞부분을 보여 줘. '사업비'라는 단어가 들어간 행도 몇 건인지 찾아봐 줄래?

## 6. 스스로 해보기: regulation 테이블과 ICT기금규정 색인 (G ~ J)

규정 문서를 위한 `regulation` 테이블을 만들고 채운다.

### 6-1. regulation 테이블 만들기 (G)

`documents`와 같은 구조의 `regulation` 테이블을 만드는 마이그레이션을 Claude에게 작성하게 한 뒤, `supabase db push`로 적용했다.

### ▶ 사용자 프롬프트 — 6-1 (regulation 표 만들기)

> `documents`랑 똑같은 구조로 규정을 담을 `regulation` 표를 만드는 변경 지시를 적어 줘. 그다음 그걸 실제 데이터베이스에 적용하고, 잘 생겼는지 확인해 줘.

### 6-2. 규정 PDF 파싱 — GPT-4o 비전 사용 (H)

`ICT기금규정/` 폴더에는 운영·관리규정, 각종 지침, 별표·별지 등 약 30개의 규정 PDF가 있다. 이 문서들은 표와 조문 구조가 복잡하다. 그래서 단순 변환 도구 대신, Claude가 만든 파싱 스크립트 `parse_regulation_pdfs.py`를 썼다.

이 스크립트는 PDF의 각 페이지를 이미지로 렌더링한 뒤, OpenAI의 이미지 인식 기능(GPT-4o 비전)으로 그 이미지를 읽어 표와 조문 구조를 보존한 마크다운으로 바꾼다. 이미지를 그대로 읽기 때문에 복잡한 표가 덜 깨진다. 변환 결과에는 정렬 순서와 출처 정보를 파일 머리말(**frontmatter**)에 적어 둔다. frontmatter는 파일 맨 위에 적어 두는 메타 정보 영역이다.

kordoc 대신 비전 기반 변환을 쓴 이유는 규정 문서의 표·조문이 복잡하기 때문이다.

### ▶ 사용자 프롬프트 — 6-2 (규정 PDF를 그림으로 읽어 풀기)

> `ICT기금규정/` 폴더의 규정 PDF들은 표랑 조문 구조가 복잡해. 각 페이지를 그림으로 만든 다음, AI가 그 그림을 보고 읽어서 표·조문이 안 깨지게 텍스트로 바꾸는 스크립트를 만들어 줘. 파일 맨 앞에는 어떤 순서로 놓을지(정렬 순서)랑 어디서 온 문서인지(출처)를 적어 줘.

### 6-3. regulation 색인 스크립트 만들기 (I)

다음으로 Claude에게 `ingest-regulation.ts`를 만들게 했다. 매뉴얼 색인과 다른 점은 자르는 기준이다. 규정은 의미가 조문 단위로 나뉘므로, **조(제N조) 단위로** 잘랐다. 한 조가 너무 길면 항 단위로 더 잘게 나눴다. 각 조각은 똑같이 OpenAI 임베딩(1024차원)으로 바꿔 `regulation` 테이블에 넣었다.

또 한 가지를 더 했다. 같은 출처를 다시 넣을 때 기존 행을 먼저 지우고 새로 넣게 했다. 그래야 같은 규정을 두 번 적재해도 중복이 쌓이지 않는다.

### ▶ 사용자 프롬프트 — 6-3 (규정 색인 스크립트 만들기)

> 풀어낸 규정 텍스트를 조(제N조) 단위로 잘라 줘. 한 조가 너무 길면 항 단위로 더 잘게 쪼개고. 각 조각을 임베딩으로 바꿔서 `regulation` 표에 넣는 스크립트를 만들어 줘. 같은 출처를 다시 넣을 때는 기존 행을 먼저 지우고 새로 넣어서 똑같은 게 두 번 쌓이지 않게 해 줘.

### 6-4. 규정 전용 검색 함수와 확인 (J)

마지막으로 `regulation` 테이블을 검색하는 전용 함수 `regulation_search`를 만들고, 적재 건수와 검색 결과를 확인했다.

### ▶ 사용자 프롬프트 — 6-4 (규정 검색 함수와 확인)

> `regulation` 표에서 질문과 의미가 가까운 조문을 찾아 주는 전용 검색 기능을 만들어 줘. 그리고 몇 건이 들어갔는지, '정산 기한'으로 검색하면 어떤 조문이 나오는지 보여 줘.

## 7. 꼭 아는 개념: 임베딩

이번 회차에서 하나만 기억한다면 이것이다.

**임베딩(embedding)** = 글을 컴퓨터가 의미로 비교할 수 있는 숫자 목록으로 바꾼 것. 이 프로젝트에서는 글 하나가 1024개의 숫자로 바뀐다. 의미가 비슷한 글끼리는 숫자도 가깝게 나온다. 그래서 단어가 똑같지 않아도 의미가 가까운 조항을 찾을 수 있다.

**임베딩 짝 맞추기 규칙.** 문서를 넣을 때(색인) 쓴 임베딩과 나중에 질문을 검색할 때(쿼리) 쓰는 임베딩은 반드시 같은 모델·같은 차원이어야 한다. 임베딩은 같은 기준으로 만든 숫자끼리만 비교가 되기 때문이다. 색인은 OpenAI로, 검색은 다른 모델로 만들면 기준이 달라 검색이 제대로 되지 않는다.

**왜 OpenAI인가.** 이 프로젝트의 임베딩은 처음부터 끝까지 OpenAI `text-embedding-3-small`, 1024차원으로 통일한다. 색인도 쿼리도 같은 모델·차원을 쓴다. 이 임베딩은 영구히 OpenAI이고 바꾸지 않는다. 즉 나중에 모델을 갈아끼우거나 다시 색인하는 일은 없다. (참고로 Cohere라는 이름이 나오더라도 그것은 임베딩이 아니라 검색 결과를 한 번 더 거르는 Rerank 단계에서만 쓰는 것이고, 이번 회차의 임베딩과는 무관하다. 임베딩은 OpenAI다.)

## 8. 핵심 용어

| 용어 | 한 줄 설명 |
|---|---|
| **바이브코딩** | 코드를 직접 안 짜고 말로 시켜 AI가 짜게 하는 방식. |
| **Supabase** | 클라우드 데이터베이스. 회원가입하면 바로 쓴다. |
| **마이그레이션** | 데이터베이스 구조를 어떻게 바꿀지 적어 둔 변경 지시 파일. |
| **테이블** | 데이터를 행과 열로 담는 표. 규정은 `documents`·`regulation`에 넣었다. |
| **파싱** | PDF처럼 글자가 박힌 문서를 검색 가능한 텍스트로 풀어내는 것. |
| **청킹** | 긴 글을 임베딩할 수 있게 적당한 크기 조각으로 자르는 것. |
| **임베딩** | 글을 의미로 비교할 수 있는 숫자 목록으로 바꾼 것. (OpenAI, 1024차원) |
| **색인** | 문서를 임베딩해서 데이터베이스에 미리 넣어 두는 것. |
| **벡터** | 임베딩(숫자 목록)을 저장하고 비교하게 해 주는 데이터베이스 기능. |
| **service_role** | 데이터베이스에 무엇이든 쓸 수 있는 권한 키. 서버·스크립트 전용, 화면 코드 금지. |
| **MCP** | Claude가 외부 도구에 직접 접속해 조회·작업하게 해 주는 연결 통로. |
| **짝 맞추기 규칙** | 색인과 쿼리는 같은 임베딩 모델·차원을 써야 한다(OpenAI 1024차원). |

## 9. 직접 만져보며 복습

다음을 직접 해 보면 이번 회차가 손에 잡힌다.

1. Supabase 화면에서 `documents`(또는 `regulation`) 테이블을 열어, 규정 조각이 실제로 들어가 있는지 눈으로 본다.
2. 한 행의 임베딩 칸을 보고, 글이 숫자 목록으로 바뀌어 있는 것을 확인한다.
3. Claude에게 다음과 같이 시켜 키워드 검색이 되는지 확인한다.
   > `documents` 표에서 '사업비'가 들어간 행 5건만 보여 줄래?
4. `.env.local`을 열어 `EMBEDDING_MODEL`이 `text-embedding-3-small`, `EMBEDDING_DIMENSIONS`가 `1024`로 되어 있는지, `SUPABASE_SERVICE_ROLE_KEY`가 화면 코드가 아닌 곳에서만 쓰이는지 확인한다.
