### 0-4. 왜 "법령 이름을 안 댄 질의"가 지금까지 안 됐나 (전반부의 뿌리)

이번 회차 전반부(백엔드)를 이해하려면 **지금 왜 안 되는지**부터 봐야 한다. 어드바이저는 **법 이름을 정확히 말한 질의만** 법령 근거를 찾는다. 원인은 한 곳, `lib/law/search.ts`의 `searchLaw`가 **법령 "이름"으로만 검색**하기 때문이다.

현재 동작 (코드 그대로):

```
질의 → extractLawNames(query)        ← 정규식으로 "○○법/시행령/규칙…" 토큰 추출 (search.ts:43, 175)
        │
        ├─ 법령명 뽑힘("근로기준법") → 법제처 target=law 검색 → ✅ OK
        └─ 못 뽑음(법 이름 없는 자연어)
              → terms = [query]        ← 자연어 전체를 검색어로 (search.ts:176)
              → lawSearch.do?target=law 는 "법령 이름" 기준 검색 → 0건
              → refs.length===0 → 빈 결과 반환 (search.ts:192) → 법령 근거 없이 답
```

| 질의 | `extractLawNames` | `target=law` 결과 |
|---|---|---|
| "근로기준법 연차 며칠?" | `["근로기준법"]` | ✅ 법령 조회 |
| "야근수당 안 주면 불법인가요?" | `[]` (법 이름 없음) | ❌ **0건** (실측 `totalCnt:"0"`) |
| "전세보증금 못 돌려받았어요" | `[]` | ❌ 0건 |

**근본 원인 두 가지:**

1. **법제처 `target=law`는 법령 "제목(이름)" 검색**이라 조문 "내용"으로는 못 찾는다. "야근수당"이라는 말은 근로기준법 **본문**엔 있어도 **법령명**엔 없으니 0건이 된다.
2. PIMS는 korean-law MCP의 도구 중 **`search_law`(제목 검색)만 내장**하고, **`search_ai_law`(조문 본문 의미검색)는 내장하지 않았다.** 그래서 "법 이름을 모르는 질의 → 법령"으로 이어 주는 경로 자체가 처음부터 없었다.

> 결국 **법을 잘 아는 사람일수록 잘 쓰이고, 정작 법 이름을 모르는 외부 기관 담당자(주 사용자)일수록 법령 근거를 못 받는** 역설이 있었다. 이번 회차 전반부(2장)는 빠져 있던 **본문 의미검색(`search_ai_law`)** 을 내장하고, 주 사용자가 법 이름을 모르므로 **제목검색을 1차로 두지 않고 처음부터 본문 의미검색으로** 찾도록 바꿔 이 구멍을 메운다.

# 전반부 — 백엔드

## 2. [백엔드] 법 이름을 몰라도 찾기 — 본문 의미검색(aiSearch) 내장

### 2-1. 무엇을 고치나

`searchLaw`(`search.ts`)는 법 **이름**으로만 검색해(0-4 참조), 이름 없는 자연어 질의는 0건이 된다. 주 사용자는 **법 이름을 모르는 외부 기관 담당자**이므로, 제목검색을 1차로 두지 않고 **처음부터 본문 의미검색(`search_ai_law`)으로 조문·법령 내용에서** 찾는다. 제목검색(`searchLaw`)은 운영 흐름에서 빼고, **인용검증의 보조(`searchByName`)로만** 남긴다.

### 2-2. 해법 — 법제처 MCP의 `search_ai_law`

법제처 MCP(**chrisryugj/korean-law-mcp**, 우리 `lib/law/`의 원형)에는 `search_law`(제목 검색)와 별개로 **`search_ai_law`(본문 의미검색)** 가 있다. 자연어를 보내면 **법제처 서버가 의미를 해석해 관련 조문을 랭킹해서** 돌려준다(엔드포인트 `lawSearch.do?target=aiSearch&search=0`, **search=0=조문**). 즉 한국 법 전체를 색인할 필요 없이 **법제처에 한 번 더 호출**하면 되고, 권장 흐름은 `search_ai_law`(발견)→`get_law_text`(전문)이지만 **aiSearch 응답에 조문 본문이 내장**돼 우리는 2차 호출 없이 근거를 구성한다. **DB 변경 없음.**

### 2-3. ✅ 실측 검증 완료 (확정 사실)

법제처 `target=aiSearch`를 실제 호출(OC=`kca-api`)해 응답 스키마와 결과를 확인했다.

| 법령 이름 없는 질의 | 재정렬 후 상위 법령(실측) | 같은 질의 `target=law` |
|---|---|---|
| "야근수당 안 주면" | 공무원수당규정 · 지방공무원수당규정 · **근로기준법**(제56·70조) | **0건** |
| "전세보증금 못 돌려받았어요" | 전세사기피해자 특별법 시행규칙 · **주택임대차보호법**(제3조의3) | **0건** |
| "직장 내 괴롭힘 신고" | **근로기준법**(제76조의3, 89%) + 판례 | **0건** |

**응답 스키마 (`target=law`와 달라 전용 파서 필요):**

| 구분 | `target=law` | `target=aiSearch` |
|---|---|---|
| 래퍼 키 | `LawSearch` | **`aiSearch`** |
| 배열 키 | `law` | **`법령조문`** |
| 항목 단위 | 법령 | **조문** |
| 법령명 필드 | `법령명한글` | **`법령명`** |
| 조문 본문 | 없음(2차 호출) | **`조문내용`·`조문제목`·`조문번호`·`조문가지번호` 내장** |

→ **(1) 전용 파서**(`parseAiSearchList`). **(2) 조문 본문 내장**이라 2차 호출 불필요. **(3) DB 변경 없음.** ※ 우리 발췌가 법제처 공식 원문(`get_law_text`)과 글자 단위로 일치함을 18개 조문 대조로 확인.

> **품질 주의 — 재정렬이 필수**: `aiSearch`는 의미 랭킹이라 곁가지 법령을 위로 낸다(예: "야근수당"→근로기준법보다 공무원수당규정이 먼저, 무관한 식품위생법·국세징수법까지 섞임). 그래서 **이미 스택에 있는 Cohere `rerank-v3.5`로 후보를 질의 기준 재정렬**해 무관 법령을 끌어내리고(내부 규정과 동일한 0~1 관련도 스케일), 답변 인용은 `verifyCitations`로 교차검증한다.

### 2-4. 내장 설계 (실제 구현)

| 단계 | 작업 | 위치 |
|---|---|---|
| 1 | `DrfTarget`에 `"aiSearch"` 추가 + `buildSearchUrl`의 `search`를 `0\|1\|2\|3`로 확장 (**`search=0`이 falsy로 빠지던 버그 수정**) | `lib/law/client.ts` |
| 2 | **전용 파서 `parseAiSearchList`** — `aiSearch.법령조문[]`(조문가지번호 포함). 판례 파서(`decisions.ts`)의 방어적 패턴 차용 | `lib/law/search.ts` |
| 3 | **`searchAiLaw(query)`** — `target=aiSearch`(search=0, display=50) → **Cohere 재정렬** → 법령ID 중복제거(상위 3법령) → **법령당 상위 3개 조문** + 관련도(`LawRef.score`). minScore 미달이면 빈 결과(엉뚱한 법령 노출 방지) | `lib/law/search.ts` |
| 4 | 법제처 분기에서 `searchLaw` → **`searchAiLaw` 호출**, 참조문서 `score`에 관련도 싣고 `content=law.articles[i]`(법령별 조문) | `app/api/chat/route.ts` |
| 5 | **인용검증 낫표(「」) 허용 수정** — `「근로기준법」 제56조` 형태를 매칭하도록 `CITATION_RE` 보강(이전엔 닫는 낫표 때문에 0건 → 환각차단이 작동 안 했음) | `lib/law/verify.ts` |
| 6 | 캐싱 자동 재사용 — `cachedGetJson(tool_name="search_ai_law")` | `lib/law/cache.ts` |

> **핵심**: 제목검색을 폴백으로 두지 않고 **처음부터 의미검색 단독**. route는 `searchLaw`→`searchAiLaw` 한 줄 교체 + score 한 줄. 그리고 **법령당 1조문이 아니라 상위 3조문**을 실어 답변이 인용하는 조문(예: 근로기준법 제56조)이 참조문서에 함께 뜨게 한다. verify의 낫표 수정으로 환각차단이 비로소 실제 작동.

### 2-5. 손대는 파일 (백엔드)

```
lib/law/
├─ client.ts ··· [1] DrfTarget 에 "aiSearch" · search 0|1|2|3 (search=0 버그 수정)
├─ search.ts ··· [2] parseAiSearchList · [3] searchAiLaw(재정렬·법령당 다중조문·관련도)
├─ cache.ts ···· [참고] 그대로 재사용 (tool_name="search_ai_law")
└─ verify.ts ··· [5] 인용검증 낫표(「」) 허용 수정
lib/ai/rerank.ts ······· [참고] 기존 Cohere 재정렬 재사용
app/api/chat/route.ts ··· [4] searchLaw→searchAiLaw, 참조문서 관련도(score)
supabase/migrations/ ····· 변경 없음 (의미검색·재정렬은 법제처/Cohere가 수행)
```

### ▶ 사용자 프롬프트 — 2장 (그대로 복사해 시키기)

> 지금 우리 챗봇은 **"근로기준법"처럼 법 이름을 정확히 말해야만** 관련 법을 찾아 줘. 그런데 우리 주 사용자는 **법 이름을 모르는 외부 기관 담당자**라, **"야근시키고 수당을 안 줘요", "전세금을 못 돌려받았어요"** 처럼 상황만 말하면 못 찾아. 그러니 **제목으로 찾는 검색을 1순위로 두지 말고, 처음부터 법제처의 '본문 의미검색'(법 이름이 아니라 조문 내용의 의미로 찾는 검색, search_ai_law)으로** 법을 찾게 바꿔 줘. 한국 법을 우리가 따로 저장할 필요 없이 **법제처에 물어보기만** 하면 돼.
>
> 이 검색은 결과가 **조문 단위**로 오고 조문 본문이 같이 와 — 그 모양에 맞춰 읽어 줘. 그리고 법제처 의미검색은 **엉뚱한 법령을 위로 올릴 때가 있으니**(예: "야근수당"에 공무원수당규정이 근로기준법보다 위), **이미 쓰고 있는 재정렬(Cohere)로 질의 기준 다시 정렬**해 무관한 법을 끌어내려 줘. 또 **법령 하나에 조문 하나만 보여 주지 말고 상위 2~3개 조문**을 같이 실어서, 답변이 인용하는 조문이 참조문서에 빠지지 않게 해 줘. 마지막으로, 답변이 **「법령명」 제○조**처럼 낫표로 인용해도 **인용검증이 그걸 인식**하도록 해 줘(지금은 낫표 때문에 검증이 0건이라 환각차단이 안 돌아).

> 붙이기 전 한 번 시켜 볼 것: "야근수당 안 주면" 같이 **법 이름 없는 질문**으로, ① 근로기준법 조문이 참조에 뜨는지 ② 답변의 「근로기준법」 제56조가 **인용검증 ✓** 로 뜨는지 확인해 줘.

# 후반부 — 화면(UI) 재구성

> 백엔드(2장)가 끝나 **검색이 제대로 찾기 시작하면**, 이제 그 결과를 사용자가 잘 보고 신뢰하도록 화면을 다듬는다.

## 3. [화면] 서버가 보내는 신호를 화면에 드러내기 (+ 공용 타입)

서버(`route.ts`)는 답변과 함께 **두 신호**를 이미 보낸다.

- **`routing`(분기 결과)**: 이 답을 내부규정으로 했는지 / 법령으로 했는지 + 관련도 점수.
- **`citations`(인용 검증)**: 답변의 법조문 인용을 법제처 DB와 대조한 결과(✓ 실존 / ✗ 없음 / ⚠ 확인불가)와 환각 여부.

그런데 화면(`page.tsx:17-21`)은 `StreamEvent` 타입에 이 두 줄이 없어 **그냥 흘려버린다.** 이걸 받아서:

- 답변 위에 **분기 줄** — "📘 내부규정 근거" 또는 "⚖️ 법령 근거(관련도 N%)".
- 답변 아래에 **인용 검증 줄** — ✓/✗/⚠.
- 확인 안 된 인용이 하나라도 있으면(`hasHallucination`) **눈에 띄는 경고 배너**.
- (작은 백엔드 1개) **진행 상태(`stage`)** — 답 시작 전 "내부 규정 찾는 중… / 법령 확인 중…" 한 줄. 이것만 서버에 단계 신호를 새로 추가한다.

그리고 같은 데이터 모양(`StreamEvent`·`SourceChunk`)을 화면·서버가 **각자 따로** 적어 둬서 어긋난다(이번에 신호를 흘린 것도 이 때문). **`lib/types.ts` 한 곳에 모아** 양쪽이 함께 쓰게 정리한다.

> **이게 후반부 1순위인 이유**: `routing`·`citations`는 **이미 서버가 보낸다.** 화면이 받아 그리기만 하면 된다 — **새 백엔드 작업은 진행 상태(`stage`) 하나뿐.**

### ▶ 사용자 프롬프트 — 3장

> 우리 챗봇 서버는 답을 보낼 때 **이 답을 '내부 규정'으로 했는지 '법령'으로 했는지**, 그리고 **답에 나온 법 조항이 진짜 있는 조항인지 공식 원문과 대조한 결과(인용 검증)**를 같이 보내고 있어. 그런데 화면이 이걸 안 받고 버려서 사용자에게 안 보여. 화면이 이 두 가지를 받아서, **답 위에 '📘 내부 규정으로 답함' 또는 '⚖️ 법령으로 답함(관련도 N%)'** 을 한 줄로 보여 주고, **답 아래에 '✓ 확인된 인용 / ✗ 확인 안 된 인용 / ⚠ 확인 불가'** 를 보여 줘. **확인 안 된 인용이 하나라도 있으면(= AI가 지어낸 환각 징후)** 눈에 띄게 **"일부 인용을 확인할 수 없어요 — 원문을 확인하세요"** 라는 경고 띠를 띄워 줘.

> 그리고 답이 나오기 시작하기 전에 **지금 무엇을 하는 중인지** 한 줄로 보여 줘 — 규정을 찾는 중이면 "내부 규정 찾는 중…", 법을 확인하는 중이면 "법령 확인 중…"처럼. 이건 서버가 지금 어느 단계인지 같이 알려 줘야 하니 **그 신호도 같이** 만들어 줘.

> 마지막으로, 화면과 서버가 **똑같은 데이터 모양을 각자 따로** 적어 둬서 자꾸 어긋나는데(방금 그 신호를 화면이 흘린 것도 이 때문), 그 모양을 **한 파일에 모아** 양쪽이 같이 쓰게 정리해 줘. 화면 동작은 그대로 두고.

## 4. [화면] 근거 보여 주는 방식 재구성

새로 들어온 판례까지 합쳐, 근거를 **한 화면에서 일관되게** 본다.

- **출처 뱃지 통일**: 지금 참조 **목록**은 회색 글씨 뱃지("법제처 법령"/"판례"/"N% 관련도")인데, **패널과 같은 색 뱃지**로 통일한다 — 📘 파랑 내부규정 / ⚖️ 보라 법령·판례. (색 뱃지는 `source-panel.tsx`엔 이미 있으니 같은 기준을 목록에도 적용.)
- **본문 `[1][2]` → 패널 점프**: 답변 본문의 근거 번호를 누르면, 오른쪽(좁은 화면은 아래) 패널이 그 근거 원문으로 이동.
- **법령 카드에 인용 검증 배지**: 법령 근거 카드 안에 그 조문의 ✓ 확인됨 / ✗ 확인 안 됨 / ⚠ 확인 불가 표시(3장의 `citations`와 연결).
- **판례 카드 정합**: 0-2에서 새로 들어온 ⚖️ 판례 카드를 같은 패널·뱃지 체계에 맞춘다.

### ▶ 사용자 프롬프트 — 4장

> 참조 문서 **목록**에서 내부 규정·법령·판례를 **색이 있는 같은 모양 뱃지**로 통일해 줘 — **내부 규정은 파란 📘, 법령과 판례는 보라 ⚖️** (지금 목록은 회색 글씨라 구분이 약해). 그리고 답 본문에 있는 **근거 번호 [1] [2]를 누르면** 오른쪽(좁은 화면은 아래) 패널이 **그 근거 원문으로 이동**하게 해 줘. **법령 근거 카드 안에는** 그 조항이 진짜 있는지 확인한 표시(**✓ 확인됨 / ✗ 확인 안 됨 / ⚠ 확인 불가**)도 같이 보여 줘. 지금 잘 되는 패널 열고 닫기는 그대로 두고.

## 5. [화면] 쓰기 편하게 — 생성 제어·편의

비전문가(외부 기관 담당자)가 쓰는 화면이라, 작은 매끄러움이 신뢰로 이어진다.

| 기능 | 무엇을 | 왜 | 현재 |
|---|---|---|---|
| **답변 복사** | 답변마다 '복사' 버튼 | 실무에서 바로 붙여 사용 | 없음 |
| **예시 질문 칩** | 빈 화면에 "이런 걸 물어보세요" 버튼 | 처음 쓰는 사람이 막막하지 않음 | 빈 화면 문구만 있음 |
| **생성 중단** | 생성 중 '전송'이 '멈춤'으로 바뀌고 누르면 즉시 멈춤 | 길거나 엉뚱할 때 바로 끊고 재질문, 비용 절감 | 없음(중단 불가) |
| **맨 아래로** | 위로 올려 읽다 새 글이 이어지면 '↓ 최신으로' 버튼 | 긴 답변·법령 원문에서 길 잃지 않음 | 스크롤 추적만 있고 버튼 없음 |

> '생성 중단'은 지금 `send()`에 요청을 취소할 수단이 없어서 안 된다 — **`AbortController`**(진행 중인 요청을 도중에 끊는 표준 수단)를 붙여 '멈춤' 버튼이 그걸 호출하게 한다. 나머지(복사·예시칩·맨아래로)는 **화면만으로** 끝난다.

### ▶ 사용자 프롬프트 — 5장

> 챗봇 화면에 네 가지 편의를 더해 줘. ① **답마다 '복사' 버튼**으로 한 번에 복사, ② 대화가 비어 있을 때 **'이런 걸 물어보세요' 같은 예시 질문 버튼** 몇 개, ③ 답이 만들어지는 동안 **'전송' 버튼이 '멈춤'으로 바뀌고 누르면 바로 멈추기**(멈춘 뒤 곧장 다음 질문 가능), ④ 위로 올려 읽다가 새 답이 이어지면 **'↓ 최신으로' 버튼**이 떠서 한 번에 맨 아래로(맨 아래에 있을 땐 안 보이게). 지금 잘 되는 대화·스크롤·패널은 **그대로 두고** 이 네 가지만 더해 줘.

## 7. 핵심 용어 (한 줄 정의)

| 용어 | 한 줄 설명 |
|---|---|
| **본문 의미검색 / search_ai_law** | 법령 **이름**이 아니라 **조문 내용**을 자연어로 찾는 법제처 검색(`target=aiSearch&search=0`). "야근수당 안 주면"으로 근로기준법을 찾아낸다. 의미검색은 법제처 서버가 수행한다. |
| **의미검색 우선(제목검색 미사용)** | 주 사용자가 법 이름을 모르므로, 제목검색을 1차로 두지 않고 **처음부터 본문 의미검색**으로 찾는 방식. 제목검색은 인용검증 보조로만 남긴다. |
| **재정렬(Cohere rerank)** | 법제처 의미검색이 곁가지 법령을 위로 낼 때, 질의 기준으로 다시 매겨 무관 법령을 끌어내리는 단계. 내부 규정과 **동일한 0~1 관련도 스케일**을 준다. |
| **`routing` / `citations`** | 분기 결과(내부규정/법령·관련도) / 인용 검증 결과(✓✗⚠·환각 여부) 스트림 이벤트. **서버는 보내는데 화면이 아직 안 받는** 두 신호. |
| **`stage`(진행 상태)** | 답 시작 전 "지금 무엇을 하는 중"인지 알리는 서버 신호. 이번에 새로 추가하는 유일한 백엔드 이벤트. |
| **인용 검증 / 환각** | AI가 댄 "○○법 제N조"를 공식 원문과 대조해 맞는 것만 남기는 것 / AI가 없는 내용을 사실처럼 지어내는 현상. |
| **판례 / 헌재결정** | 법령 분기 시 함께 조회하는 법원 판례(`prec`)·헌법재판소 결정(`detc`). 판시사항·판결요지를 근거로 보강. |
| **공용 타입(lib/types.ts)** | 화면·서버가 함께 쓰는 데이터 모양. 지금은 세 파일에 흩어져 중복 — 한 곳으로 모은다. |
| **`AbortController`** | 진행 중인 요청을 도중에 취소하는 표준 수단. '생성 중단'에 쓴다. |

## 8. 직접 만져보며 복습하기 (회차 후)

1. **법 이름을 댄 질문**("근로기준법 연장근로 한도")과 **법 이름을 안 댄 질문**("야근수당 떼였어요") 둘 다에서 **법령 근거가 붙는지** 확인한다(2장의 핵심).
2. 내부규정에 있는 질문 → 답변 위 **'📘 내부규정 근거'**, 없는 법령 질문 → **'⚖️ 법령 근거(관련도 N%)'** 로 바뀌는지 확인(분기 줄).
3. 일부러 **없는 법조문**으로 유도해, 답변 아래 **'✗ 확인 안 됨' + 경고 배너**가 뜨는지 확인(인용 검증).
4. 법령 분기 질문에서 **판례 카드(⚖️ 판례)** 가 근거에 함께 뜨고, 참조 **목록·패널 뱃지 색이 통일**됐는지 확인.
5. 답변 본문의 `[1][2]`를 눌러 **패널이 해당 근거로 이동**하고, **복사·예시칩·중단·↓최신으로**가 동작하는지 확인.

---

> 이 회차를 마치면 **(전반부) 법 이름을 몰라도 상황만으로 법령 근거를 찾고, (후반부) 백엔드가 보내던 신호가 화면에 드러나며 근거·편의가 정리된다.** 이로써 어드바이저 ①은 "내부규정 → 법령(이름·의미검색) → 판례 → 인용 검증"이 한 흐름으로 완성된다. 다음은 7월 — **Vercel 오픈 환경설정과 오픈 전 보안 하드닝**(로그인 게이트·레이트리밋·색인 API 차단·에러 일반화)이다.
