# ① 규정·법령 어드바이저

> 한 줄 요약: 사용자가 질문하면 **ICT기금 내부 규정**을 먼저 찾아보고, 규정만으로 답하기 충분하면 규정으로, 부족하면 **법제처 법령**까지 끌어와 **출처가 붙은 믿을 수 있는 답변**을 만들어 주는 챗봇입니다.

> 일정: **2026년 5~7월**. PIMS 첫 번째 모듈이자 핵심 가치 모듈.

> 이용 대상: ICT기금 외부 기관 담당자. **로그인 필수**.

---

## 1. 목표

- ICT기금 **내부 규정·지침·해석사례**를 1차 근거로, 필요할 때 **국가법령(법제처)** 을 2차 근거로 더해, 질문에 **출처가 명시된 신뢰 가능한 답변**을 만든다.
- AI가 지어내는 가짜 정보(환각, hallucination)를 막기 위해, 답변에 등장한 **법령 인용을 법제처 공식 원문과 자동으로 대조**한다.
- 더 나아가 **공모사업 공고**(② 크롤러가 모으는 `announcements` 데이터)까지 같은 챗봇 화면에서 답하도록 **3개 정보원(내부 규정·법령·공모 공고)을 하나의 답변으로 통합**한다. 단, 셋을 항상 합치지 않고 **질문에 맞는 정보원만 골라 부르는 방식**으로 통합한다. (상세: 7장. 공모 공고 통합은 8월 예정)

> 용어 한 줄 정의
> - **RAG**: 질문과 관련된 문서를 먼저 찾아서 그 내용을 근거로 AI가 답하게 하는 방식.
> - **임베딩**: 문장을 숫자 벡터로 바꿔, 의미가 비슷한 글을 가까운 위치에 두는 기술.
> - **재정렬(Rerank)**: 1차로 찾은 후보들을 질문과의 실제 관련도로 다시 줄 세우는 단계.

## 2. 입력·출력

### 입력

```json
POST /api/chat
{
  "query": "사업비 집행 시 증빙서류는 어떤 것이 필요한가?",
  "session_id": "uuid (옵션)",
  "user_id":    "uuid (옵션)"
}
```

### 출력

`text/plain` **스트리밍**(답변이 완성될 때까지 기다리지 않고 글자가 생기는 대로 화면에 흘려보냄). 응답이 끝나면 `query_log` 테이블에 비동기로 기록한다.

### 예시 답변 구조

```
1. 결론
   사업비 집행 시 증빙서류는 ...

2. 적용 조항
   - 「ICT기금 운영규정」 제12조 제2항 (출처: ICT-OP-2024-008)
   - 「국가재정법」 제54조 (출처: 법제처 법령 ID 12345)

3. 적용 시 유의사항
   ...

4. 근거 목록
   [1] ICT기금 운영규정 제12조 제2항 (2024.05.17 시행)
   [2] 국가재정법 제54조 (2023.12.31 개정)
```

## 3. 한눈에 보는 처리 흐름

```
사용자 질문
   │
   ▼
[1] 내부 규정 검색 (OpenAI 임베딩으로 질문을 벡터화 → hybrid 검색, 후보 약 30건)
   │
   ▼
[2] 재정렬 (Cohere Rerank, 상위 약 8건 + 각 건의 관련도 점수)
   │
   ▼
[3] 관련도 분기  ◀── 이 모듈의 핵심
   ├─ 상위 결과 관련도 ≥ 기준치 → 내부 규정만 근거로 답변
   └─ 상위 결과 관련도 <  기준치 → 법제처 OpenAPI 직접 호출(자체 구현 도구)로 법령·판례 조회 + 인용 검증
   │
   ▼
[4] Claude 답변 생성 (스트리밍)
   │
   ▼
[5] query_log 비동기 적재 (질의·답변·근거·관련도·분기 결과·지연·토큰)
```

핵심은 **RAG와 법령을 항상 합치지 않는다**는 점이다. 내부 규정만으로 충분하면 법령을 부르지 않고, 부족할 때만 법령을 끌어온다. 둘 중 하나로 **분기**한다.

> 위 흐름은 현재의 **2개 정보원(내부 규정 + 법령)** 기준이다. 여기에 **공모 공고**를 더한 3개 정보원 통합 설계는 7장에서 다룬다. 공모 공고도 내부 규정과 같은 방식(OpenAI 임베딩 검색)으로 찾으므로, [1][2] 단계에 검색 대상 테이블을 하나 더 얹는 형태로 같은 라우팅에 자연스럽게 들어온다.

---

## 4. RAG 파이프라인 (단계별 상세)

### Step 1. 내부 규정 검색 (Hybrid Search)

- 질문을 **OpenAI `text-embedding-3-small`(1024차원)** 임베딩으로 벡터화한다.
- Supabase RPC `hybrid_search` / `regulation_search`를 호출한다.
  - 대상 테이블: `documents`, `regulation`
  - 방식: **BM25(키워드 매칭) + pgvector(의미 유사) + RRF(두 결과를 합치는 방법)**
  - 결과: 후보 **약 30건**

> 색인(문서 저장)과 쿼리(질문 검색)는 **동일한 OpenAI 임베딩**을 쓴다. 이 임베딩은 **영구 유지**하며, 교체하거나 다시 색인하지 않는다.

### Step 2. 재정렬 (Cohere Rerank)

- **Cohere `rerank-v3.5`** 로 후보 30건을 질문과의 관련도로 다시 줄 세워 **상위 약 8건**을 고른다.
- Rerank는 벡터가 아니라 **질문과 문서의 원문 텍스트**를 직접 읽고 점수를 매긴다. 그래서 임베딩 모델과는 별개의 단계다.
- 각 결과에는 **관련도 점수**가 붙는다. 이 점수가 다음 분기의 판단 기준이 된다.

### Step 3. 관련도 분기 (핵심)

상위 결과의 관련도 점수를 **기준치(threshold)** 와 비교한다.

| 조건 | 동작 | 근거 |
|---|---|---|
| 관련도 **≥ 기준치** | 내부 규정만으로 답변 | 내부 규정·지침·해석사례 |
| 관련도 **< 기준치** | **법제처 OpenAPI 직접 호출**(자체 구현 도구 `lib/law/`)로 법령·판례 조회 → 인용 검증 | 내부 규정 + 법제처 법령·판례 |

- 내부 규정에 답이 분명히 있으면(점수가 높으면) 법령을 부르지 않아 **빠르고 정확**하다.
- 내부 규정만으로 부족하면(점수가 낮으면) **법제처 법령·판례**를 추가로 가져와 답의 근거를 보강한다.

### Step 4. Claude 답변 생성

- 모델: Anthropic **Claude `claude-sonnet-4-6`**
- **스트리밍** 출력 + **프롬프트 캐싱**(고정 시스템 프롬프트를 캐시해 비용·지연을 낮춤).
- Step 3에서 모은 근거(내부 규정, 그리고 필요 시 법령·판례)를 컨텍스트로 받아 답을 만든다.

### Step 5. 로그 적재

- 매 질의·응답을 `query_log`에 **비동기로**(응답 속도에 영향 없이) 적재한다.
- 기록 항목: 질의, 답변, 근거, 관련도 점수, 분기 결과(규정/법령), 지연 시간, 토큰 수.
- 관리자 화면에서 통계와 세부 내역을 조회한다.

## 5. 법령 조회 — 법제처 OpenAPI 직접 호출 (자체 구현 도구)

내부 규정만으로 부족할 때(관련도 < 기준치), 법령 정보는 **법제처 국가법령정보 공동활용 OpenAPI**(`lawSearch.do`/`lawService.do`)를 **직접 호출하는 자체 구현 도구**(`lib/law/`)로 가져온다. `LAW_GO_KR_API_KEY`(OC 인증값)를 사용한다.

> **왜 자체 구현인가**: 개발(Claude Code) 환경에서는 korean-law MCP를 쓰지만, MCP 서버는 Vercel 서버리스 함수 런타임에 상주할 수 없다. 그래서 MCP가 제공하던 것과 **동일한 기능을 `lib/law/`에 자체 함수로 구현**했다. 데이터 출처는 여전히 **법제처**(국가법령정보)이고, 인용 검증과 `law_cache` 캐싱도 그대로 유지한다. 도구 이름(`search_law`, `get_law_text`, `verify_citations`, `search_decisions`, `get_decision_text`)도 MCP의 도구 구성을 참고해 그대로 쓴다.

### 자체 구현 법령 도구가 제공하는 기능

| 도구(함수) | 구현 파일 | 설명 |
|---|---|---|
| `search_law` | `lib/law/search.ts` | 법령명·키워드로 법령 목록(명·시행일 등) 조회 |
| `get_law_text` | `lib/law/search.ts` | 특정 법령의 조항 본문 그대로 가져오기 |
| `search_decisions` / `get_decision_text` | `lib/law/decisions.ts` | 판례(target `prec`)·헌재 결정(target `detc`) 검색 및 본문 확인 |
| `verify_citations` | `lib/law/verify.ts` | AI가 댄 "○○법 제○조"가 실존하는지 + 현행/폐지 여부 검증 (환각 방지 핵심) |

> 공통 전송 계층은 `lib/law/client.ts`(법제처 DRF 전송, `target` 파라미터로 법령·판례·헌재 구분), 캐싱은 `lib/law/cache.ts`(`law_cache` 테이블)가 담당한다.

### 동작 방식

- Claude가 답을 만들다가 법령 근거가 필요하면, 위 도구를 호출해 법제처 OpenAPI에서 **공식 원문**을 받아 온다.
- 받아 온 원문을 근거로 답을 작성하므로, 임의로 지어낸 조문이 답에 섞이지 않는다.

## 6. 환각 방지 — 인용 검증

법령 인용을 답변에 넣을 때, 자체 구현 법령 도구의 **인용 검증**(`verify_citations`) 기능으로 법제처 공식 원문과 대조한다.

### 흐름

1. AI가 답변에 "근로기준법 제53조: 사용자는 1주 12시간을 한도로 …"처럼 인용을 만든다.
2. 인용 검증이 해당 법령·조항의 **공식 원문**을 조회한다.
3. AI가 인용한 내용과 공식 원문을 **대조**한다.
4. **맞는 인용만** 근거로 채택한다. 일치하지 않으면 답변을 고치거나 "확인되지 않음"으로 명시한다.

> 효과: AI가 그럴듯하게 지어낸 가짜 조문이 답변에 남는 것을 막는다. 이 모듈의 가장 큰 가치다.

## 7. 통합 설계 — 3개 정보원(규정·법령·공모) 결합

같은 챗봇 화면에서 **내부 규정·법령·공모 공고** 세 가지를 모두 답할 수 있게 통합한다. 사용자(외부 기관 담당자)의 질문은 자주 정보원을 가로지르기 때문이다. 예를 들면:

- "이 공모사업 신청 자격이 우리 규정상 되나?" → **공모 + 규정**
- "정산 기한이 법령과 우리 규정이 다른가?" → **규정 + 법령**
- "지금 신청 가능한 ICT 공모 있어?" → **공모**(시의성 중요)

### 7-1. 세 정보원의 성격

| 정보원 | 어디에 있나 | 어떻게 찾나 | 특별히 중요한 점 |
|---|---|---|---|
| **내부 규정** | Supabase `documents`·`regulation` | OpenAI 임베딩 검색 + Cohere 재정렬 | 기관 권위 문서 |
| **공모 공고** | Supabase `announcements` (② 크롤러 적재) | OpenAI 임베딩 검색 | **시의성**(접수·마감일) |
| **법령** | 법제처(국가법령) | 실시간 조회 + 인용 검증 | 최신성·정확 원문 |

> 핵심 구분: **내부 규정과 공모 공고는 같은 방식**(우리 데이터베이스의 임베딩 검색)이라 통합이 쉽다. **법령만 외부 실시간 조회**라 통합의 관건이다.

### 7-2. 통합 방식 — "골라서 부르는" 라우팅

세 정보원을 매번 다 부르면 느리고 비싸고 출처가 뒤섞인다. 그래서 **질문에 필요한 정보원만 고른다.**

```
질문
 │
 ├─[1] 가벼운 의도 분류 (규정 / 공모 / 법령 / 복합)
 │
 ├─[2] 내부 검색(규정 + 공모) → Cohere 재정렬 → 관련도 점수
 │       ├ 관련도 ≥ 기준치 → 내부 근거로 답 (법령 호출 안 함)
 │       └ 관련도 < 기준치 또는 '법령' 의도 → 법령 조회 + 인용 검증
 │
 ├─[3] 복합 질문만 도구 호출(tool use)로 여러 정보원을 차례로/병렬 조회
 │
 └─[4] Claude가 고른 근거를 종합 → 스트리밍 답변 + 정보원별 출처 표시
```

- **단순 질문**은 빠른 경로(분류 + 단일 검색)로, **복합 질문**만 도구 호출 경로로 보낸다. (단순한 것에 비용을 아끼고, 어려운 것에 깊이를 준다.)
- 3장의 **관련도 분기**를 그대로 확장한 형태다. 공모 검색은 [2]에 테이블만 추가하면 된다.
- 복합 질문용 도구(tool use) 예: `search_regulation`, `search_announcements`, `search_law`(+`verify_citation`). Claude가 필요한 도구만 호출한다.

### 7-3. 런타임에서 법령을 부르는 방법 (확정)

`korean-law MCP`는 **개발(Claude Code) 환경의 도구**다. 프로덕션 서버(Vercel 함수)에서 매 질문마다 로컬 MCP를 띄우면 **콜드 스타트 지연**(수 초)이 생기고, 애초에 MCP 서버는 서버리스 함수 런타임에 상주할 수 없다. **→ 자체 함수 구현으로 직접 호출 확정.**

- **법제처 OpenAPI 직접 호출(자체 구현)** — 이미 `LAW_GO_KR_API_KEY`(OC 인증값)를 보유. MCP가 제공하던 기능을 `lib/law/`에 자체 함수(`client.ts`/`search.ts`/`verify.ts`/`decisions.ts`/`cache.ts`)로 구현했다. 단일·결정형 호출에는 직접 호출이 가장 단순·빠르고, 인용 검증·`law_cache` 캐싱도 그대로 유지한다.

> 사용자 화면에는 "법령(법제처)" 출처로 보이며, **런타임 구현은 법제처 OpenAPI 직접 호출(자체 구현 도구) + Claude 도구 사용**이다.

### 7-4. 사용자 화면(UX) 설계

통합의 가장 큰 위험은 **출처 혼동**(공고를 규정처럼, 일반 정보를 법령처럼 받아들이는 것)이다. 그래서 출처 구분이 UX의 핵심이다.

| UX 요소 | 내용 | 이유 |
|---|---|---|
| **출처 타입 뱃지** | 📋공모공고 / 📘내부규정 / ⚖️법령 구분 표시 | 근거의 성격을 즉시 구분 |
| **정보원별 근거 섹션** | 답변 하단에 정보원별로 묶고 원문 링크 제공 | 클릭해서 직접 검증 |
| **스트리밍 중간 상태** | "내부 규정 검색 중… 법령 확인 중…" 표시 | 도구 호출 대기 체감 단축 |
| **공고 신선도** | 접수 D-n / **마감됨** 표시, 마감 공고 필터 | 만료 공고로 인한 오답 방지 |
| **법령 인용 검증** | 검증 통과분만 근거로, 미검증은 "확인되지 않음" | 가짜 법조문 차단 |
| **되묻기·예시 질문** | 모호하면 정보원을 유도하는 질문 칩 | 분류 오류 보완 |

답변 형식은 기존과 동일: **결론 → 정보원별 근거 → 유의(규정·법령 차이, 공고 마감, 검증 결과)**.

### 7-5. 위험과 완화

| 위험 | 완화 |
|---|---|
| 도구 호출로 인한 **지연** | 라우팅으로 호출 정보원 최소화 + 병렬 검색 + 스트리밍 중간 상태 |
| **출처 혼동** | 출처 타입 뱃지·정보원별 섹션·시스템 프롬프트에서 출처 표기 강제 |
| **만료된 공고** 안내 | `announcements` 마감일 메타데이터를 검색 단계에서 필터 |
| **가짜 법조문** | 인용 검증 통과분만 근거 채택 |
| **비용 증가** | 관련도 기준치로 법령·복합 경로 최소화, 프롬프트 캐싱 |

### 7-6. 단계별 도입

1. **현재(6월)**: 내부 규정 RAG + 재정렬 + 관련도 분기 + 법령(법제처 OpenAPI) → **2개 정보원 통합 + 출처 뱃지** 검증.
2. **8월**: 크롤러가 `announcements` 적재 → `search_announcements` 추가 → 라우터에 3번째 정보원 등록 + 공고 신선도 UX.
3. **이후**: 복합 질문용 도구 호출 오케스트레이션 정교화 + 관리자 로그의 분기·정보원 통계로 라우팅 품질 튜닝.

> 한 번에 셋을 다 붙이지 않는다. **2개 정보원으로 통합 패턴(라우팅·출처 구분)을 검증한 뒤** 공모 공고를 끼워 넣는 것이 위험이 가장 낮다.

## 8. 시스템 프롬프트

```
당신은 ICT기금 규정·법령 어드바이저입니다.

[원칙]
- 제공된 <context>의 내부 규정·지침·해석사례와 (있을 경우) 법령·판례만 근거로 답변합니다.
- 컨텍스트에 없는 사실은 추측하지 말고 "확인된 자료에 없습니다"라고 명시합니다.
- 모든 인용에 출처(법령명·조항·내부문서번호)를 반드시 표기합니다.
- 법령 인용은 자체 구현 법령 도구(법제처 OpenAPI)의 인용 검증(verify_citations)으로 공식 원문과 대조된 것만 사용합니다.
- 답변 끝에 "근거" 섹션을 두고 번호와 출처를 나열합니다.

[답변 형식]
1. 결론 (2~3줄)
2. 적용 조항·규정 요약 (인용 포함)
3. 적용 시 유의사항
4. 근거 목록
```

→ 고정 부분에 `cache_control: { type: "ephemeral" }` 를 적용해 **프롬프트 캐시**로 비용·지연을 줄인다.

## 9. 관리자 화면 — 채팅 로그 + 공모 크롤러 운영 통합

관리자 기능은 **하나의 챗봇 관리자(admin) 화면**으로 통합한다. 채팅 로그 분석과 공모 크롤러 운영을 별도 도구로 나누지 않고 같은 화면에서 다룬다. (운영자가 한 곳에서 보고 관리하도록.)

### 9-1. 채팅 로그·통계 (어드바이저 운영)

`query_log`에 쌓인 데이터로 다음을 분석한다.

- **통계(집계)** — 일·주별 질의 수, 기관별 사용량, 정보원 분기 비율(규정/법령/공모), 평균 응답 지연, 토큰·비용 추이.
- **세부 조회** — 개별 대화의 질문·답변 전문, 사용한 근거와 관련도 점수, 어느 기관이 물었는지. 기간·기관·키워드·정보원으로 필터.
- **답변 품질** — 인용 검증 통과 비율, 사용자 피드백 평균.
- **FAQ·추천 질문** — 비슷한 질문을 묶어(클러스터링) 빈도 상위를 FAQ로 추천.

### 9-2. 공모 크롤러 운영 (② 크롤러 관리 통합)

② 크롤러(`announcements` 적재)의 관리 기능도 **같은 관리자 화면 안의 별도 탭/섹션**으로 넣는다. 챗봇이 공모 공고를 정보원으로 쓰는 만큼, 그 데이터의 수집·품질을 같은 곳에서 관리하는 것이 자연스럽다.

| 기능 | 내용 | 데이터 |
|---|---|---|
| **수집 소스 관리** | 크롤링 대상 사이트 등록·수정·on/off | `crawler_sources` |
| **실행 이력 모니터링** | Cron 실행 결과(성공·실패·수집 건수), 실패 알림 | `crawl_runs` |
| **공고 분류 검수** | AI 분류 결과(ICT기금 여부·카테고리)를 사람이 확인·수정 | `announcements` |
| **수동 재실행** | 특정 소스를 즉시 다시 수집 | — |
| **공고 현황** | 접수 중 / 마감 임박 / 마감 공고 목록과 통계 | `announcements` |

> 통합의 이점: 운영자가 **"챗봇이 무엇을 답하는가(로그)"** 와 **"그 근거 데이터가 어떻게 들어오는가(크롤러)"** 를 한 화면에서 함께 본다. 예를 들어 특정 공모 질문의 답이 이상하면, 같은 화면에서 그 공고의 수집·분류 상태를 바로 확인할 수 있다.

### 9-3. 접근 권한

- **관리자 권한 사용자만** 접근한다(일반 외부 기관 담당자는 챗봇만 사용, 관리자 화면 접근 불가).
- 채팅 로그에는 개인·기관 식별 정보가 있으므로 권한 분리를 명확히 한다(보안·운영 정책은 `docs/07` 참조).

## 10. 평가 셋

PoC 종료(7월말) 전 다음을 평가한다.

| 지표 | 목표 |
|---|---|
| 내부 규정 검색 Recall@8 | ≥ 0.85 |
| 인용 검증 통과율 | ≥ 0.95 |
| 사용자 만족도 (5점 척도) | ≥ 4.0 |
| 첫 응답 시작 시간 (TTFT) | ≤ 3초 |
| 응답 완료 시간 | ≤ 15초 |

평가 셋: ICT기금 운영팀이 작성한 골든 Q&A 50~100건.

### 품질이 목표에 못 미치면 (개선 방향)

임베딩은 OpenAI로 **고정**이므로 교체하지 않는다. 품질은 아래로 끌어올린다.

- **Rerank 기준치 튜닝** — 관련도 분기의 기준치를 조정해, 규정/법령 분기 비율과 정확도의 균형을 맞춘다.
- **청킹 개선** — 문서를 자르는 단위·크기를 조정해 검색 적중률을 높인다.
- **프롬프트 개선** — 시스템 프롬프트와 답변 형식을 다듬어 답의 정확도·가독성을 높인다.
